Pantry row actions on desktop

Desktop. Mockup, nothing built. Kitchie #866, 17 Oct 2026.

On the phone, a Pantry row is swiped: left a little to use one, left a long way to use it up, right to add it to the shopping list. The owner: “For Pantry items, Kitchie allows these mobile swipes, but that is not the right way to do it on a desktop. I want mockups for how we navigate this idea for the desktop. I want to see some options.” Four options are drawn below on the settled desktop Pantry (rail, column, side panel), each covering every swipe action, a keyboard way, a touch-laptop fallback, and the empty and edge states, in dark and light. The phone and its swipe are unchanged.

Recommendation: A, plus Use one added to the panel. It is the Shopping desktop pattern the owner already approved (hover buttons with key caps, shown on hover, focus and the current row), it adds nothing at rest, it is one click, and it is the only option that puts all three actions on the row. The panel gets Use one beside Used up and Add to shopping list so the open item offers every swipe action too (D’s one good idea, without its keys line). B waits until there are more actions than three, because it takes over right click on a real link. C waits until there is a real need to act on several items, because it is the only one that needs a new write path. Stop a mouse drag swiping a row on desktop.
Stress test: what the owner could push back on, and the answer
  • “Hidden until hover means nobody finds it.” A shows on hover, on focus and on the current row, with key caps, so moving the mouse over a list is enough, and a tap or J / K keeps them up. D has no hidden part; its keys line is always there. If the owner still doubts A, the cheap fix is the label on the first row for the first visits (client-side, like the phone’s nudge).
  • “Screen space is precious.” A, B and C add nothing at rest and change no row, header or list height. D adds one 36px line, which the cues switch hides.
  • “Used up is one click next to the cart.” It is the far-right button, as the tick is today, 6px from the cart, red only on hover, with the 5 second Undo bar, Z, and the server’s third-in-five-minutes guardrail, which A to D now ask about in place instead of pointing at the item.
  • “Two code paths, one for the phone and one for the desktop.” No. Every option calls the swipe’s own act() and shop(), as the keys and the item sheet already do. Only the control that triggers it differs, and it lives in desktop-pantry.js, which a phone never downloads (DA-D3). The one shared-file edit is that a mouse pointer stops starting a swipe.
  • “Right click is the browser’s.” The strongest case against B. The row is a real link, so B hides “Open in new tab” and “Copy link” (Shift right click gives them back).
  • “Who selects five pantry items?” Unknown; there is no evidence yet of a bulk job. C is the only option that is not a thin trigger on an existing call: one used-up is fine, three or more would trip the removal guardrail and the per-member write limit if looped.
  • “An iPad in landscape, a touch laptop.” They get the desktop layout and have no hover. Each option shows its controls on the tapped row at 44px, and swipe still works for a finger. Covered by the touch checks.
  • “Tab through forty rows.” A adds a third stop to each row (today two). The keys are the fast path; the buttons stay real buttons for screen readers. Left as it is (DA-Q11).
  • “A used-up item vanishes.” It goes to Out, stays findable by search and the Out chip, and Undo brings it straight back.
Choices the mockup made where the owner was silent (Proposal; what a wrong guess costs)
  • DA-P1 Every swipe action stays reachable on desktop, each with the same 5 second Undo bar and Z. Wrong guess: none, this is the job.
  • DA-P2 One code path: every option calls the swipe’s act() and shop(). No new route for A, B or D.
  • DA-P3 A mouse drag on a row no longer swipes on desktop; touch and pen still do. Wrong guess: someone who dragged with the mouse loses it; one line brings it back.
  • DA-P4 Touch laptop or tablet landscape: swipe stays, and the tapped (current) row shows the option’s controls at 44px, chosen by the hover capability in CSS, not by width.
  • DA-P5 Level-only rows have no Use one (as today); the U key says why. Out rows offer Add to list only.
  • DA-P6 Words: Use one, Add to list, Used up on the compact buttons; Add to shopping list in the menu, the panel and the lane (the item sheet’s words).
  • DA-P7 Order: Use one, Add to list, Used up, the tick last where it is today.
  • DA-P8 In A the use-by words hide while the buttons show, and the name ends in an ellipsis before them.
  • DA-P9 Add to list from the desktop behaves like the S key: it sends the item panel’s “How much to buy” words at Running low or Out; the swipe sends none today.
  • DA-P10 The used-up guardrail is asked in place: the bar says “Several items were used up just now. Use up peas anyway?” with Use up and Not now. Today’s words are at ?guard=today. Needs the reduce route to accept a confirm (Build impact).
  • DA-P11 Key caps use the shared kbd class and follow the Shift Space cues switch.
  • DA-P12 In C, once a row is picked a plain click on a row picks or unpicks it; the item opens again when nothing is picked.
  • DA-P13 In B the menu closes with the owner’s close chord, a click outside or a choice, not plain Esc.
Open questions (recommended position first)
  • DA-Q1 Which option? Recommended: A, with Use one added to the panel. Cost of a wrong pick: a mockup edit; nothing is built.
  • DA-Q2 Does a mouse drag stop swiping on desktop? Recommended: yes (DA-P3). It fights text selection and click-to-open, and nobody asked for it on a desktop.
  • DA-Q3 Touch laptop: keep swipe and show the controls on the tapped row? Recommended: yes (DA-P4).
  • DA-Q4 Ask the used-up guardrail in place (DA-P10)? Recommended: yes, as its own later slice, because it changes a write path. Until then today’s message stands and points at a dead end.
  • DA-Q5 Add to list on an Out row from the row? Recommended: yes; an item that ran out is the one you want to buy.
  • DA-Q6 Several items at once (C), now or later? Recommended: later, when there is a real case (for example clearing five things after a cook). Cost of waiting: none; of building now: a guarded write path for a job nobody has named.
  • DA-Q7 A context menu as well as A? Recommended: not now; right click stays the browser’s.
  • DA-Q8 Should the row’s Add to list ask how much to buy? Recommended: no, as the S key today (DA-P9).
  • DA-Q9 Does a menu or selection close with plain Esc? Recommended: no, keep the owner’s close chord (Esc leaves full screen); revisit if B is chosen.
  • DA-Q10 Is hiding the use-by words while the buttons show acceptable? Recommended: yes; the words return as the pointer leaves, and they are in the panel. If not, the buttons can shrink to icons only.
  • DA-Q11 One more Tab stop per row in A? Recommended: leave it; J / K and the keys are the fast path.
Build impact
No migration, in any option. No schema, no stored data, no new setting (remembered choices stay client-side).
  • Recommended (A plus Use one in the panel, no mouse drag): routine. Touches desktop-pantry.js (the Add to list button and key caps on each row, desktop only, fetched only from 64rem), desktop-css/pantry.ts (the strip), the desktop item panel (one button), swipe.js (pointer type, one line, input not viewport, the only shared-file edit), the swipe test and a new desktop browser journey. No deny-list path, no new route: act() and shop() have several callers and are not edited. Wrong build costs: a missed hover state on a row, a use-by label hidden; both visible in the browser journey.
  • B: routine. Same files plus the menu; the cost is the lost right click on a link, not a build risk.
  • D: routine. Panel button and a keys line.
  • C: guarded. Several used-ups need a batch route (a new write path in web-edit.ts and the store, which is on the deny list): looping the single call trips the third-in-five-minutes guardrail and the per-member write limit. It needs a risk package.
  • The in-place guardrail confirm (DA-P10, DA-Q4): guarded, separate slice. The reduce route accepts exactly one field today; a confirm field relaxes the removal guardrail on a write path.
What this loads (DESIGN.md section 6)

The default path is desktop.html, rows.css, rows.js, act.js and sample.js on top of theme.css, then only the chosen option’s two small files (opt-a.css and opt-a.js, and so on); the other three are never requested (checked). In the app nothing new is fetched: the controls are drawn by desktop-pantry.js, which a phone never downloads, and the actions are changed in place with the Undo bar, not by reloading (section 6a). Checked at 1024, 1280 and 1440 wide in light and dark, with a mouse and a touch laptop, with tools/pantry-row-actions-check.mjs.
