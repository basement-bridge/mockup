Pantry and Recipes on desktop: what the side panel shows when nothing is picked

Mockup for the owner to review. Options to choose from, nothing built (Kitchie #867).

Owner, by voice, 17 October 2026: “Under Pantry and Recipe there is a flyout that is blank. Under Recipe it says ‘pick a recipe to see it here’; under Pantry it says ‘pick an item to see it here’. That seems pretty ordinary, but what are your design options for that space when something is not picked?” Six directions are drawn for both screens, in dark and light, for an empty household, a typical one and a large one (420 items, 180 recipes). Every one is built only from what the list page already holds, so none of them asks the server for anything.

The small bar at the bottom of each screen (“Mockup only”) switches option A to F, household size and touch. Click any name in a pane to open it in the lane; Ctrl or Cmd with Esc closes it and the pane comes back.

What it is today

From 1024px up, the Pantry and Recipes keep a 400px lane on the right even when nothing is open. The only thing in it is one line of muted text, drawn by CSS alone (a ::after in desktop-layout.ts for the Pantry and desktop-css/recipes.ts for Recipes): “Pick an item to see it here.” and “Pick a recipe to see it here.” It costs nothing to load, and it also teaches nothing and answers no question. About 400 by 800 pixels of the screen (a third of it) is idle every time you arrive.

The recommendation: F, for both screens

F: the at-a-glance pane, trimmed to the two or three things that need you, with one line of keys at the foot. It answers the question a person has when they land on the page and have not picked anything (“what needs me?” on the Pantry, “what can I cook?” on Recipes), it matches Home’s tiles so nothing is new to learn, and it costs no request. When there is nothing to say, it says exactly what it says today, so no household ever sees an empty summary. It is the same shell for both screens (header, blocks, key line), so the build is one component with two block lists.

Why not the others. A is F with more, and too tall for a laptop. B repeats the + and Filters that are already on screen. C is a nice extra but empty at first and tied to one browser; it can be added under F later. D is a one-off lesson that Shift+? already gives. E is the cheapest, but on a 1280px screen it only moves the empty space to the right.

Wide tablet (1024px, no keyboard)

At 1024px the lane is still 400px and the list column narrows to fit. With touch there is nothing to press keys on, so the key line becomes “Tap an item to open it.”, and D shows a tap line instead of its list of keys. Every control in a pane is 44px or more high on desktop and tablet alike (checked). Below 1024px the lane is not drawn and nothing here applies (the phone keeps its own pattern).

Decisions for the owner (pick one answer for each)
  • EP-1 Which direction? Recommended: F for both screens. A, B, C, D and E are drawn and can be switched to at the bottom bar. Combining (F now, C added under it later) is allowed.
  • EP-2 One shared shell for Pantry and Recipes, or a different idea on each? Recommended: shared (same header, block, key line; only the blocks differ).
  • EP-3 When nothing needs attention: today’s one line (recommended), or a friendly all-clear (“Nothing is going off. Nothing is running low.”, drawn in A)? The line keeps the screen as quiet as today; the all-clear tells you it looked.
  • EP-4 Keep the key line at the foot (recommended: a pointer user sees / search, up and down move, ? all shortcuts), or leave it out?
  • EP-5 Is a person’s own “last opened” (C) wanted now? Recommended: not now; it is kept per browser and so is empty on first use.
Choices the mockup made where the owner was silent (Proposal)
  • EP-P1 Proposal. The pane replaces the one-line text in the same 400px lane, with the same surface, border and 24px padding as the item panel, so opening something changes the content and nothing else moves.
  • EP-P2 Proposal. A block head is a button that applies the same filter Home’s tiles do (Use soon, Running low, Ready now), and the list then shows exactly that many rows. No new filter is invented. Planned this week and Cooked lately are plain labels because the Recipes list has no such chip.
  • EP-P3 Proposal. A name in a block opens that item or recipe in the lane, the same as clicking its row; closing it (X, or Ctrl or Cmd with Esc) brings the pane back and focus returns to the row.
  • EP-P4 Proposal. F shows two names per block (three for Ready now) and “and N more”, which is the filter. Use soon is sorted by date, soonest and overdue first, never A to Z.
  • EP-P5 Proposal. “Use soon” means a use-by within 7 days or overdue; “Running low” is the existing low flag. Both are what Home already uses, to be confirmed against Home’s tile before build.
  • EP-P6 Proposal. The numbers are never separate from the list: a count is the number of rows its filter shows. This is a build test (the mockup check does it for A and F in both households).
  • EP-P7 Proposal. An empty household gets prompts, never a summary of nothing: Pantry says “Your pantry is empty” with Add an item and Scan a receipt; Recipes says “No recipes yet” with Ask your assistant to add one (recipes are added through the assistant).
  • EP-P8 Proposal. F leaves Out items out of the pane. The default Pantry list hides them on purpose (data-gone, Kitchie #329), so a block that shows them would disagree with the list the person is looking at. Out stays one tap away in Filters.
  • EP-P9 Proposal. If the pantry cannot be read, Recipes F says “Kitchie cannot read the pantry right now, so it cannot say what is ready.” and shows no Ready now block.
  • EP-P10 Proposal. The key line shows on a keyboard device only. On a touch tablet it reads “Tap an item to open it.”
  • EP-P11 Proposal. The pane re-counts from the rows whenever the list changes (use one, used up, a filter), with no request, so it cannot drift out of date while it is on screen.
  • EP-P12 Proposal. The recommended pane is no taller than 768px at any household size (checked), so it never scrolls on a small laptop. A is allowed to be taller and is, for that reason, not the pick.
Open questions (recommended position first; what a wrong guess costs)
  • EP-Q1 (owner is working on lazy loading) If the list will load in pages, counts must not be taken from the rows loaded so far. Recommended: the server writes the pane (or just its numbers) in the same query that writes the list, so they cover every row; the pane still needs no request of its own. Cost of a wrong guess: the pane says 6 use soon, the filter shows 4 until you scroll, and the person stops trusting it. This is the one thing to settle before building.
  • EP-Q2 Recipes “One thing short” (drawn in A, not in F) needs a missing-ingredient count per row. The list today carries only data-ready (all in or not). Recommended: leave it out of F. Cost to add later: one data attribute, no new request.
  • EP-Q3 Should Planned this week and Cooked lately become chips in the Recipes list so their heads can be buttons? Recommended: not in this change; they stay labels (EP-P2). Cost: two inert-looking heads that do not open anything.
  • EP-Q4 Use soon at 7 days (EP-P5): is that Home’s rule? Recommended: use Home’s, whichever it is. Cost if different: the pane and Home disagree about the same item.
  • EP-Q5 Do large households want a longer pane (A) instead of F’s trimmed one? Recommended: no; “and N more” opens the full filtered list, which is where a long list belongs.
  • EP-Q6 If C is added later, per browser (recommended, nothing stored on the server) or per person across devices? Across devices needs a stored table, which is a migration; per browser needs none.
Stress tests (headless Chromium, 1280 and 1024, dark and light: tools/empty-pane-check.mjs, 1005 checks pass)
  • Every option draws (or, for E, deliberately draws nothing) for every household: empty, typical, large, calm, and for Recipes the pantry-unreadable case, on both screens.
  • The number in a block equals the rows its filter then shows (Pantry A and F, Recipes A and F, typical and large). The pane cannot disagree with the list.
  • No request of any kind (fetch or XHR) at load, on a name click, or on closing.
  • Every control in a pane is 44px or more high; no sideways scroll at 1024 or 1280; no page errors.
  • Empty households get a way forward and never a summary; calm households get today’s one line with no blocks.
  • A name opens its item; Ctrl or Cmd Esc brings the pane back; / still focuses search.
  • E: at 1280 the list is already capped at 640px, so collapsing buys no width; below about 1224 the list moves when the lane opens. Recorded as the cost of E.
  • F is no taller than 768px in the typical or large household, on both screens.
What the default path loads, and what is deferred (DESIGN.md section 6)

Built, F adds no request on the default path: the numbers and names come from the rows the page is already built from (data-useby, data-low, data-gone on the Pantry; data-ready, data-cd, data-planned on Recipes), or from the same query that writes them (EP-Q1). Nothing is deferred because nothing extra is fetched. Today’s pane is CSS only; F adds a small block of markup and a few lines of script in the existing desktop-pantry.js and recipes-desktop.js (the whole mockup pane, with all six options, is 20 KB raw and 5.2 KB gzipped plus 5 KB of CSS; F alone is a fraction of that, an estimate of 2 KB gzipped). The receipt scan engine is not loaded by the pane; it loads only when Scan a receipt is pressed. This page loads theme.css, shared.css and screenshots on demand (lazy).

Build impact (verdict)

No migration. No schema change, no new table, no new endpoint, no new MCP tool. The change replaces the CSS-only text in server/src/desktop-layout.ts and server/src/desktop-css/recipes.ts with a small pane drawn from data the pages already hold. Option C, if added, uses browser storage only (EP-Q6); a per-person history across devices would need a table and is not part of F. A change to the lane’s width, the item panel or the lists is not needed. Per AGENTS.md, the build copies this mockup’s markup and CSS (.ip, .ip-blk, .ip-bh, .ip-li, .ip-act, .ip-keys, .ip-foot, .ip-quiet) first. Mockup-only: the sample data, the toast, the fake “when” words and the switcher bar.
