Proposing a preference for another member

One housemate notes something about another ("Sam avoids peanuts"). It goes straight onto Sam's own list, is used at once, and Sam is told at their next login and can keep it, change it or remove it. The person who proposed it is never told what Sam decided. Not an approval gate. Built on option B's layout.

What this option does

The owner's shape (voice, 10 October 2026), recorded as C-D1 to C-D4, and the ten decisions locked later that day, recorded as D5 to D14 below. It is not a hard approval gate. Option C itself, and every open question below, is awaiting approval.

  • C-D1Any member proposes for another member. Preferences > Mine > Food > Add something for a housemate. Pick the person, say what (avoids, dislikes, likes, usually) and the thing.
  • C-D2It is written on the subject's own list from the start. Not on the household list and not in a shared bucket. The record belongs to Sam and is tagged proposed by Arjan, with a pending flag (chip Waiting for you on Sam's list).
  • C-D3It takes effect at once. Recipe building and planning read it straight away, so an allergy does not wait for Sam to log in. The proposer's screen says so in three lines before the button, and again after.
  • C-D4Sam gets a courtesy notice at the next login (a banner, plus a standing row Added for you). Three answers: Keep it as it is (clears the pending flag, keeps the attribution), Change it (Sam's version replaces the value), Remove it (the record is gone).

What the code holds, and what would have to change Checked 10 Oct 2026

Read again on the default branches: Kitchie main 7e6fd08, Recipe main 5cec532, platform main 409f44f. Summary and sources: docs/knowledge/user-preferences/option-c-propose-for-another-member.md.

  • Today a member can only write their own record or the household's. give_feedback takes who as "me" or "household", and the member always comes from the link, never an argument. There is no way to write on another member's list. Change: name the subject member, checked server side as a member of the same household.
  • Person-level food statements exist (context_claims, member_id set). Change: add proposed_by, proposed_at, an acknowledgment state (pending, accepted, edited) and when; rejected is the existing retired status.
  • Any member can write a household claim today (D8 kept that; D28 now says only household admins may, so that is a code change in front of the chat tool too) and nothing addresses a claim to a member. There is a household-changes banner (joins and removals, dismissed per member, deleted after 60 days) and "new" badges, but nothing to claim back. Change: the notice can be a query over pending records on the member's own list, so no queue table is needed; only the "Later" dismissal needs storing.
  • Reads stop at the caller. get_context returns the caller's own and the household's; "another member's are never read", and plans carry for_whom but do not read anyone's claims. For "planning picks it up right away" to be true, the plan and recipe read must include the avoidances of each member the meal is for. That is a change to the visibility rule, and it also applies to Sam's own avoidances today.
  • Accept, edit, remove map to existing feedback kinds (accepted, corrected, a retire) but v1 only notes accepted and never acts on it; here it would clear the flag. Tool texts say everything returned was stated and Established: a proposal is stated by someone else, so it needs its own source.
  • No outcome goes back to the proposer (D11), so no event, queue or table is needed for it, and nothing in the pending state expires or escalates (D12).
  • Recipe stars and votes stay household only and platform stores no preferences (its token carries sub, household, products, times): option C changes neither. It is a Kitchie change, plus a web page for food statements, which does not exist yet (option B proposed one).
