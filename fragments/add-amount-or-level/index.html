Add item: an amount or a level

Kitchie #1047. When someone adds an item, Add asks for a number of units. Some people, in some cases, will want to give a level instead (Plenty, Some, Running low, Out). Five ways to let them, drawn on the Add sheet. Mockup only, nothing built, options not decided. Drawn from Kitchie uat at 83180cc (v0.159.0, 22 October 2026). Tap anything in a frame: it works, and the dashed box under each frame says what Add would store.

What the code already does (read from uat 83180cc, not run)
  • The web Add route already accepts a level and stores it as the person's own (web-edit.ts, the add branch). Add simply does not draw the Level control (decisions 78 and 128). So a build is the control, not a new route or field.
  • Level and quantity are two separate stored objects and never overwrite each other (R25). The level words and the three squares do not change.
  • The shopping list reads a level only when there is no exact amount (store.ts, the loose-level pass). A level-only item, or one with free words, at Running low or Out is listed as "running low" or "out", with no minimum. A level next to an exact amount is not read: the amount decides, and only against a minimum. This is what separates the options.

Proposals (the mockup's own choices, the owner was silent)
  • A, with C as the runner-up if Add must stay exactly as quiet as today. A is the quantity editor's own idea (two explicit states, R25), the owner preferred "choose between them", and nothing is hidden. D is drawn because he floated "one or the other"; it is not recommended.
  • Quantity is the default, as Add is today, so nothing changes for anyone who never switches.
  • Only the side showing is saved. What was typed on the other side stays in the form while it is open, so a flip back loses nothing, and the readout says it was not saved.
  • The last choice is remembered on this device only, not for the household (design principle: preferences are client-side).
  • No square is preselected: nothing is invented for the person. Add with Level showing and no square saves just the name, and the cue reads "Automatic".
  • Minimum stock is not drawn on the Level side: a level has nothing to compare against.
  • Tapping the picked square again takes it back, and the circular arrow does the same (the Edit flyout's "Set by you" cue, decisions 111 and 112). The words are the form's own: Quantity, Level.
  • E, for the owner's three-way reading: Words is the default (as Add is today). Switching away keeps what was typed, unsaved, and the readout says so. Not recommended over A: it separates one stored quantity into two sides, but it is the literal split asked for.
  • The same control in the quick-add sheet and the desktop Add flyout, since they are one form. Not drawn separately at 1280; confirm there.
Open (what a wrong guess costs)
  • Which option? Wrong A: one extra row for people who only count. Wrong C: Level stays hard to find. Wrong D: a mixed household is stuck on one way of adding.
  • Default to Quantity, or open on the last choice? Wrong "last choice": Add opens on Level for someone who is counting milk, one tap to flip. Wrong "always Quantity": a Level person flips on every add.
  • Should a person be able to give both (B)? If yes, a level beside an exact amount is stored but ignored by the shopping list, and the form should say so.
  • Preselect Plenty? Wrong "no": one extra tap on every add. Wrong "yes": a state the person never gave.
  • Words and a number: two choices or one? E asks the person to pick before typing. Today the editor takes either in one place and splits a plain "2kg" into 2 and kg by itself (decision 121). Wrong E: a person who types "2 jars" in Words gets free text the list cannot read. Wrong A: a person who wants words has to see a number editor first.
  • Whether the quick-add sheet should offer it at all, or only the full Add.

Loads: static HTML for each frame, theme.css, the Edit flyout's flyout.css (the shared form family), ael.css and ael.js, all cached after the first frame. No request after that, no image, no font. Frames load on scroll (loading="lazy"). In the build there is no new request: the level picker is the one Edit already draws, so the cost is the markup of one control on Add and a few lines in the form script that already loads.
