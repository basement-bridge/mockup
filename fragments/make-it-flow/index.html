Make it: chat and screen, one flow

Kitchie issue #781. Three options for how starting to make something works, drawn as live flows: the assistant's chat on the left, the phone on the right. Tap in the phone or press the buttons. Mockup only, nothing is saved or sent. The owner has not chosen. The Make it buttons on Plan, Home and Recipe are drawn in fragments/make-it (#779); here they are plain stand-ins, only the place a tap starts from.

Original problem statement (owner, by voice, 15 October 2026)

On the Make it work: “there's an MCP for start cooking … we should use most of the UI things … just the DRY principle. Then what I need there is the MCP tool, when somebody starts cooking and it's associated with the recipe … it needs to follow the same flow.” Decided: one flow for chat and screen, through the same service methods; reuse the existing screens; the word is Make it (the renamed Cook now).

  • Today, screen: Cook now opens the step-by-step cook page and starts no session. No screen path starts a session.
  • Today, chat: start_cooking starts a Cooking now session (banner on five tabs, ingredients screen, up to two at once, cleared after 45 minutes, by Done cooking, or by stop_cooking). With a recipe_id it only links to the saved recipe, as a secondary option.
  • Read from Kitchie uat v0.122.2 (issue #781), not run. Personal link only: the shared link refuses start_cooking.

Recommendation

Option 1 agent recommendation. It is the owner’s sentence taken literally: the tool and the Make it button call the same start method, and the existing screens are reused without a second mechanism. It costs a route and wording, needs no schema change, and leaves the approved tool shape alone. Option 2 leaves the screen path unable to start anything, which is the gap he named. Option 3 is the largest and pulls a recipe-level state into Kitchie, which holds no recipes. Caveats to settle first: how a duplicate start is joined (MF-P1) and what keeps a screen-started session alive past 45 minutes (MF-P5).

Proposals (the owner was silent)
  • MF-P1. A dish already live is joined, not doubled (options 1 and 3). Key: the recipe id, else the title. Today each call without a session id begins a new session. Wrong guess costs: two cards of the same dish, or two different dishes with one title merged.
  • MF-P2. The banner opens the cook page when a recipe id exists (1 and 3); without one it opens the ingredients screen. This is #781 question 2; the owner has not answered.
  • MF-P3. The two screens link to each other. The cook page has an Ingredients row that opens the tick list; the tick list has a row (“Open the cook page”, today “Browse the recipe”) that opens the cook page. Nothing from Cooking now is lost.
  • MF-P4. Done on the cook page ends the session (1 and 3), the same end method as Done cooking. In option 2 it does not.
  • MF-P5. Activity restarts the 45 minutes from the screen too (1 and 3): a tick, a step, or tapping Make it on a live dish. Today only the assistant’s next call restarts it, so a session started on the screen would clear in the middle of a long cook. Wrong guess costs: a change to cooking.ts timing, or a dish vanishing from the banner mid-cook.
  • MF-P6. The button changes while it is live (1 and 3): Back to it instead of Make it, so a second tap does not look like a restart. Option 2 keeps Make it.
  • MF-P7. A screen start carries the dish, its ingredients with amounts, by: user, source app. Where the web route reads a saved recipe’s ingredients (the Recipe service, or the plan entry) is open.
  • MF-P8. The person’s screen does not jump when chat starts a cook: the banner appears and they tap it. No auto-navigation.
  • MF-P9. Option 2 hides Make it on a made-up meal (nothing to open) and says so.
  • MF-P10. Option 3 shows a Making now chip on the recipe and the plan meal, and Done marks the meal made.
  • MF-P11. The tool’s reply and description gain one sentence about where the banner opens. The input shape does not change, but the text is part of the approved contract fixture.
  • MF-P12. Make it follows the personal-link rule (question 3): a signed-in member only; the shared link does not show it. Wrong guess costs: a guest on the shared link sees a button that refuses.
  • MF-P13. Mock stand-ins. The clock is simulated; the banner CSS is drawn from cooking-banner.ts because page.css was not found; Home and Plan are placeholders for the #779 screens; two dishes only, so the “third is kept but hidden” rule is described, not drawn.
Open questions
  1. Option 1, 2 or 3? A wrong guess costs a route and wording for 1 or 2, a schema change for 3.
  2. Does the banner open the cook page when a recipe id exists (#781 question 2), or stay on the ingredients screen? Drawn as the cook page for 1 and 3 (MF-P2) with a row to the tick list.
  3. Personal link only (#781 question 3): does Make it follow the same rule, a signed-in member only (MF-P12)?
  4. The MCP tool shape was approved on 8 October 2026. None of the options changes its input. Option 3 may need a plan entry id; MF-P11 changes the description text. Any change needs the owner.
  5. Can the assistant see a cook started on the screen? No tool reads sessions today, so after a screen start it may say “starting” for something running. MF-P1 absorbs the duplicate; the owner may want a read as well.
  6. MF-P5 and MF-P4: may screen activity keep a session alive, and does Done on the cook page end it?
  7. Made-up meals on the Plan: does #779 show Make it on them? Options 1 and 3 need it to; option 2 cannot.
