Locations and spots, three ways

Fragment. Settings > App (called Kitchen until 11 Oct 2026) already lets you rename a category for every item at once. Locations (Fridge, Pantry, Freezer) and the spots inside them (Door, Crisper, Top shelf) need the same, but a spot lives inside a location, so a flat list is not enough. Three ways to manage that. I would think about what's the best way to tackle that."Owner, voice, 8 October 2026. A design-options request, not a build. Not in the household flow yet.

Same item rules under all three (the options differ in how you get to them, not in what they do)
  • OwnerA spot is a child of one location. Renaming a location or a spot updates every item stored there at once, like categories.
  • ProposalRemove and merge are one action: "Move items to...". Pick an existing spot or location and the items go there. No default is picked for you; the button stays off until you choose.
  • ProposalMoving a spot to another location takes its items with it. A name already used there blocks the move.
  • ProposalRemoving a location moves its items to another location and keeps its spots (same names merge) unless you choose to drop them, then items land with no spot.
  • ProposalAn item can sit in a location with no spot ("Not in a spot"). A spot name is unique inside its location, not across locations. The last location cannot be removed.
  • ProposalRemoving something that holds nothing asks one plain confirm, no destination. Every change shows an Undo toast. Reorder uses buttons, not drag.

Lived in has Fridge (with a few items in no spot), Pantry, and an empty-of-spots Freezer. Brand new shows the first-time empty state.

Open questions
  • Can a spot belong to two locations (one "Door" for fridge and freezer), or is each spot owned by exactly one? This mockup: one parent, same names allowed in different locations.
  • Can items sit in a location with no spot? This mockup says yes. A wrong guess means either blocking adds that name only a location, or forcing a spot on every item.
  • Does the real Kitchie model allow renaming a location, and does a rename update items (like categories) or are items matched by name? Not checked here.
  • Terminology: the household flow and code say "area" for the parent. The owner says "location". Which word does the person see?
  • When a location is removed, should its spots default to kept or dropped? This mockup keeps them.
  • Should flows that already name a place (filters, scan-in shelf, item sheet) follow a rename live? Assumed yes, since the id stays.
  • Who can change them: anyone in the household (like people settings) or only the owner? Not decided.
  • Which option leads, or does a large household want 2 and a small one 1?
Performance note (DESIGN.md section 6)
  • Default path loads: this page, the shared theme and one inline script. No images, no icon files; the glyphs are plain text and emoji.
  • Deferred until engaged: in the real app the screen needs only location and spot names with item counts. Rename, move and remove sheets and the destination picker are built when opened. Other themes are separate files fetched on choice (theme.js).
  • Why reasonable now: it is a settings screen reached on purpose, so a small counts query on entry is enough. Each option notes anything extra above.
