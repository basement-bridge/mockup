One dialog pattern

Mockup only. Nothing built in Kitchie, nothing approved. Owner (Arjan), voice, 31 October 2026: JavaScript and CSS minimal and used the same way everywhere; one shared dialog component, one stylesheet block, no per-dialog markup. This page shows one dialog / sheet pattern with a header, a close, actions, focus and keyboard behaviour, drawn for the phone (bottom sheet with grab bar) and the desktop (centred modal and a non-modal side flyout), light and dark, with every old variant mapped onto it. Anything the owner did not state is marked Proposal. The real, working version is the sample app: open it, press Tab and Escape, resize the window. Every frame below is that same page in an iframe.

Evidence this rests on (Kitchie uat audits, not re-audited here)

About 20 hand-written role=dialog sites in 18 files, none using native <dialog>. Nine close idioms (data-close, data-close-sheet, data-closea, data-fly-close, data-hm-close, data-sheet-close, data-act=closesheet, data-sh=close, data-sheet-dim) and seven close classes (x, ib, pf-x, sib, icon, close, grab). .btn is redefined in about 14 files plus layout.ts (min-height 40, 44, 46, 48 or 52; radius 14.4px, 12px or 14px; pill 99px; weight 600, 700 or 800). .ib is 44, 40 or 38px. --dim has four values. Sheet and scrim rules sit in 15 files.

Default-look principle

Always cater for a default state. A plain <dialog class="dialog"> with a head, one body and optional actions is already correct: sheet on the phone, centred modal from 600px, closable, focus-safe, in both themes, with no modifier class and no script-set style. Every other look (dialog--flyout, btn--block, data-locked) is an opt-in on top of that, never a prerequisite. A page also keeps a default without script: a real link closes the dialog, a server-rendered <dialog open> is already visible.

1 · The pattern

Native <dialog> plus one 27-line helper. showModal() already gives Escape, the focus trap, an inert page and focus restore, so none of that is written by us. The stylesheet is 46 lines: one .btn, one .close, one .dialog. The <dialog> element is itself the scrim, so there is no scrim element.

<dialog class="dialog" id="d-confirm" aria-labelledby="d-confirm-t">
  <div class="dialog__body">
    <div class="dialog__head">
      <i class="dialog__grab" aria-hidden="true"></i>
      <h2 id="d-confirm-t">Throw out Oat milk?</h2>
      <button type="button" class="close" data-close aria-label="Close"></button>
    </div>
    <p>It moves to History. Undo stays for 5 seconds.</p>
    <div class="dialog__foot">
      <button type="button" class="btn btn--ghost" data-close autofocus>Cancel</button>
      <button type="button" class="btn btn--primary" data-close="done">Throw out</button>
    </div>
  </div>
</dialog>
<button class="btn" data-open="d-confirm">Throw out</button>
PartWhat it is
.dialogThe <dialog>. Fills the screen, carries the scrim colour (--dim). Click on it (not on the panel) is a backdrop click.
.dialog__bodyThe panel. Scrolls; head and foot are sticky.
.dialog__head, .dialog__grabTitle (h2, named by aria-labelledby), the close button, and the grab bar (drawn on the phone only).
.dialog__footActions, optional. Cancel first, the main action last.
.btn + --primary --ghost --pill --blockThe one button. Tokens: 44px (--tap), --r-ctl, weight 700.
.close (+ --plain)The one close: 44px circle, 1px border; the glyph is drawn by CSS.
dialog--flyoutSide flyout from 1024px, non-modal. Below 1024px the same markup is a normal sheet or modal.
data-open="id", data-close[="value"], data-lockedThe only three attributes. Close works on a button or a link (the value becomes returnValue). Locked: no close button drawn, Escape and backdrop ignored.

2 · Phone: bottom sheet

Under 600px the panel sits on the bottom edge, full width, rounded on top, with the grab bar. The phone is not changed by this proposal except where section 6 lists it.

3 · Desktop: centred modal and side flyout

From 600px the same markup becomes a centred modal (the grab bar is hidden). A flyout is the same markup plus dialog--flyout: from 1024px the helper opens it with show(), so it is non-modal and the page beside it stays usable; below 1024px the helper calls showModal() and it is an ordinary sheet or modal.

Decisions

Numbered DLG-D1 and on, a new series. Nothing here was stated by the owner except the goal in the first paragraph; all else is Proposal. None is confirmed.

  • DLG-D1 (Owner goal, 31 Oct). One shared dialog component, one stylesheet block, no per-dialog markup; JavaScript and CSS minimal and used the same way everywhere.
  • DLG-D2 (Proposal). Native <dialog> everywhere, opened with showModal(). Hand-written role=dialog and aria-modal go.
  • DLG-D3 (Proposal). One helper (dialog.js, 27 lines): [data-open], [data-close], backdrop click, upgrade of a server-rendered <dialog open>, [data-locked] cancel gating, show() for flyouts, focus return for flyouts. Nothing per dialog.
  • DLG-D4 (Proposal). One stylesheet block (dialog.css, 46 lines): tokens, .btn, .close, .dialog, __body, __head, __grab, __foot. Replaces the audit's .dialog / __scrim / __body / __head / __grab list by folding the scrim into the <dialog> element (no scrim element, ::backdrop unused) and adding __foot for sticky actions.
  • DLG-D5 (Proposal). One close idiom: the attribute data-close, on a button or a link; its value becomes the dialog's returnValue. The nine old idioms go.
  • DLG-D6 (Proposal). One .close (44px circle, 1px border) with a --plain variant; the glyph is CSS, markup carries only aria-label.
  • DLG-D7 (Proposal). Actions live in .dialog__foot, Cancel first, main action last, autofocus on the safe action. On the phone the actions share the row; from 600px they sit right, at their own width.
  • DLG-D8 (Proposal). Phone under 600px: bottom sheet with grab bar. 600px and up: centred modal, panel width from the token --dialog-w. Flyout from 1024px: non-modal, --flyout-w wide, full height, no scrim, no scroll lock; below 1024px it is the ordinary sheet or modal. The two breakpoints are the repo's existing literals.
  • DLG-D9 (Proposal). Scroll lock is CSS only: html:has(dialog:modal). No script toggles a body class.
  • DLG-D10 (Proposal). Works without script: close is a real link where it can be, and a server-rendered <dialog open> is visible before the helper runs. The ?param sheets stay.
  • DLG-D11 (Proposal). Non-dismissible flows use data-locked: the close button is not drawn (CSS), Escape and backdrop are ignored. The only way out is an action in the foot.
  • DLG-D12 (Proposal). Default-look principle: a plain .dialog with no modifier is complete and correct in both themes and without script; variants only add.
  • DLG-D13 (Proposal). Tokens only, no width literals: new tokens --dialog-w, --flyout-w, --grab-w, --grab-h, --z-dialog sit in dialog.css; the rest come from theme.css.
  • DLG-D14 (Proposal). Stage 1 leaves alone profile.js (profile window), pantry-receipt.js and receipt-scan.js (receipt scan). Everything else in the mapping table moves.
  • DLG-D15 (Proposal). Mockup and build share class names and data attributes exactly. The build copies dialog.css and dialog.js first and lists each difference in its pull request. dp.css, frame.html and the scaling script are mockup scaffolding and are not lifted.
  • DLG-D16 (Proposal). No animation in stage 1.

Open questions (owner picks)

  • DLG-O1 to DLG-O6 are the visible changes in section 6, each recommended there. A wrong guess costs a visible regression at 14 sites; the fix is one token.
  • DLG-O7 Swipe down on the grab bar to dismiss? Not in stage 1 (it is decoration only), because it needs pointer handling that is not 27 lines. Wrong guess: people try to swipe and nothing happens.
  • DLG-O8 Is Sign in again really non-dismissible? Drawn locked as the one example of cancel gating. If it can be dismissed, nothing else uses data-locked and it can be dropped from the helper.
  • DLG-O9 Lightbox: today a dark full-bleed viewer (not re-checked). As a default dialog it becomes a framed image with a title and a close. Keep the old full-bleed look as a second variant (more CSS) or accept the framed one?
  • DLG-O10 Tablet (600 to 1023px): a centred modal like the desktop, or keep the bottom sheet up to 1023px? Drawn centred. This is the one place the phone-sized look would change on a small tablet.
  • DLG-O11 Is a destructive button style needed (Throw out in danger colour)? Not drawn; one more modifier if yes.
  • DLG-O12 Should data-open be in the helper? It saves a click handler in every page script, at about 3 lines. Drawn in.
