Mobile Home: a quiet way to switch views

Desktop drops the Compact toggle. Compact lives on mobile: Home can be seen in full, or compact and ask-first (“What are we eating?”, one answer, nothing else). This page draws five ways to switch, each nearly invisible (an icon or a gesture, never a labelled toggle or a pill), remembered on this device, with a one-time hint. Sample data; the controls work in place; Theme button bottom right. Phone width only.

Owner, voice, 22 Oct 2026 (“build, build, build”): desktop drops the Compact toggle entirely. Compact lives on mobile: Home can be viewed compact (ask-first, “What are we eating?”) or in the fuller view. A few options for the control. Not a plainly labelled toggle, not a Dashboard / Compact segmented control, not chunky widget-style pills, no pins that expand on mobile. A very intuitive, almost invisible control, icon-level or gesture-level, not a widget sitting on the page. Each shows how a first-time person finds it (one quiet hint, shown once, no coachmark spam) and how it shows the mode without text. Persisted per person, client-side only. Screen space is precious; thumb-reachable; reduced motion; accessible names; state never by colour alone.

Recommendation

B, the pull handle, with the choice remembered as drawn. It is the only one that costs no distance for the thumb, earns its space (about 36px net) in the one place the thumb already rests, shows its own state by shape, has a visible affordance even if the hint is missed, and works with a single tap for anyone who cannot drag. Fallback if you want the cheapest and most findable: A (about 30 lines, no gesture file), at the price of the far top corner. E is not a control: use it under B or A if you want Home to adapt, never alone. C is not recommended (it switches off browser pinch-zoom on Home, an accessibility regression; and nobody finds it). D is only worth it if Home gets search anyway.

Honest trade-offs on discoverability

  • Quiet and findable pull against each other. The quieter the control, the more the one-time hint carries. A hint shown once to a person who looks away is lost for good; the control must therefore still be findable without it (A and B are, C and E are not).
  • The default hides the feature. Home opens full, as today. Someone who never meets the control never sees compact. That is deliberate (nothing changes for them) but it means usage may be low; there is no usage data here to say.
  • No coachmark spam, and no repeat when nothing can remember. When localStorage is unavailable the hint is not shown at all, because it could never be marked as seen. Those people can still use the control; they are simply not taught it.
  • State shown without text. Every option changes shape (glyph, chevron, dot count) as well as the page itself. The heading also changes wording (a greeting when full, the question when compact), which is content, not a label.

The remembered choice

  • Rule (owner): a remembered-choice UI setting is client-side only, never server-side. It is localStorage, per device.
  • Keys: kitchie.homeView.<memberId> holds full or compact; kitchie.homeView.hint.<memberId> holds 1 once the hint has shown; for E only, kitchie.homeView.learn.<memberId> holds the run count. The member id is in the key so a shared tablet remembers each person. The mock uses a mock. prefix per option so the options do not overwrite each other.
  • Survives reload: yes. Try it: in the Live frame switch the view, press Reload frame, and it reopens in the same view with the readout showing the stored value. Per device: another device, or another browser profile, starts at the default.
  • Storage unavailable (private window, cleared site data, a browser that blocks it, quota): every read and write is in try/catch; Home opens full (today’s Home); the control still works for this visit, in memory; the hint is not shown; nothing throws and nothing is shown to the person. Tick “Storage blocked” in the Live frame and press Reload frame to see it.
  • A bad stored value (anything but full or compact) is ignored: default view.
  • Another tab on the same device changing it updates this one (the storage event).

Proposals (the owner was silent; each is mine)

  • MV-P1 The default is Full when nothing is stored or storage is unavailable, so nothing changes for people who never find the control. Wrong guess costs: compact stays hidden from people who would like it; one constant.
  • MV-P2 The key carries the member id (per person on a shared device). Wrong guess costs: a new person on a shared device starts at Full; the key suffix.
  • MV-P3 Compact on mobile is the greeting becoming “What are we eating?”, the lead idea (the planned meal, else the top idea) with Make it and Plan, and one line of plain text for what is going off or running low. No tiles, no other ideas, no pills, no search. The line is text, not a control (the owner ruled out pins that expand). Wrong guess costs: the line may be wanted as a link; one element.
  • MV-P4 The hint shows once per person per device, for five seconds, goes on any touch, is marked as shown the moment it appears (not when dismissed), and is never shown when storage is unavailable. Wrong guess costs: a person who misses it never sees it again, or a longer time is wanted; one number.
  • MV-P5 In A and D the glyph shows the layout you are in (rows when full, one card when compact), and pressed also draws a ring and fills the button. The accessible name is constant (“Just tonight’s answer”) with aria-pressed, and a polite live region says what changed. Wrong guess costs: some will read the glyph as the target, not the state; swap the two glyphs.
  • MV-P6 Gesture thresholds: B drags 32px (a tap under 6px also toggles, and Enter or Space for keyboards); C pinches below 0.75 or above 1.33 of the starting finger distance, or holds 450ms; E needs three visits in a row of the same kind. Wrong guess costs: feel, one number each.
  • MV-P7 B starts only on the handle, so it never competes with the page scroll; C scopes pinch to the Home scroller with touch-action: pan-y.
  • MV-P8 D adds a search field to mobile Home (about 52px in both views), because the lens needs a field to live in. Not asked for. Wrong guess costs: a field nobody wanted, or this option is dropped.
  • MV-P9 The choice changes Home only; nothing else reads it. It is not synced to a second device (the owner rule). Wrong guess costs: a person on phone and tablet sets it twice.
  • MV-P10 Motion is one 180ms fade of the changed parts, the hint’s fade, and (A, D) two rings or (B) two nudges. With reduced motion: none of them; A and D show one still ring, B the bubble only, and the handle does not follow the finger.
  • MV-P11 Every gesture has a single-finger, no-timing alternative: B a tap, C Enter or Space on the heading, E a tap on the heading. (WCAG 2.5.1 and 2.5.4.)
  • MV-P12 Phone width only (under 600px). The drawn frame is 390 by 760. At 600px and over, Home is full and the stored choice is ignored. Wrong guess costs: see MV-Q3.

Open questions, with what a wrong guess costs

  • MV-Q1 Which control? Recommendation B, fallback A. Cost of choosing wrongly: the control is one small component; the stored value, the compact content and the keys are the same for every option, so switching later changes one file and a hint.
  • MV-Q2 Default for a new person: Full (drawn) or Compact? Full changes nothing for anyone. Compact makes Home the ask-first screen for everyone, which is a larger decision than a control. Cost: wrong default means most people see the other view first.
  • MV-Q3 Tablet. Home is full at 600px and over here. Should a tablet get the switch? Cost: a few lines of CSS and the same script; the owner has not said.
  • MV-Q4 What compact shows when nothing fits or nothing is planned. Only the “a lead idea” state is drawn. The phone pane’s own empty state (freezer meal, Ask your assistant) is the likely answer; the desktop near-misses (compact-home-options A and C) would need a phone cut. Cost: a half-empty compact screen in those states.
  • MV-Q5 Should Home ever change the view by itself (E)? Recommendation: no, unless the owner wants it; a person is surprised once and may not know why. Cost if built wrongly: a support question.
  • MV-Q6 Per person on a shared device (drawn) or per device? Cost: the key suffix.
  • MV-Q7 Does the owner want search on mobile Home? If yes, D comes back into play at no extra space cost beyond the field itself.

What loads

Default path: this page, theme.css (two themes inline), theme.js, home-view.css (about 11 KB raw, phone only), home-view.js (about 7 KB raw, mostly comments: storage, the view attribute, the icon button, the hint) and mock.js (about 20 KB, the mockup’s own sample data and frames, never for the build). No images, no fonts beyond the theme, no framework, no network call. Only the option you choose is drawn (the others are not built into the page until you open them). Deferred: gestures.js (about 6.5 KB raw: the drag handle, pinch, press and hold, the learner) is fetched only when B, C or E is opened; A and D, the icon options, never load it. In the build the same split holds: the icon switch ships in the Home bundle; gestures load on first Home paint after the page is idle, or never for a person who switches by icon. Any non-default theme is one small file fetched on choice.

For the build
