The Plan button is the working example: "Open AI on this device" on an empty week (`assets/plan.js:324`, `:391-396`) calls `window.openAssistant({prompt})` (`assets/assistant-link.js:71-90`), which reads the `kitchie_assistant` cookie (one connected: that app; two or more: the chosen default; none: no link), copies the message and opens `https://claude.ai/new?q=<prompt>` in a new tab (`:24`, `:64-69`). For ChatGPT it opens `https://chatgpt.com/?q=`, for Gemini `https://gemini.google.com/app?q=`, and for Another/none it only copies. Whether the web `?q=` is honoured is not confirmed (ADR `docs/adr/plan-week-assistant.md:49-53`: reported broken for Claude web since Oct 2025, undocumented for ChatGPT and Gemini); the copy is the safety net.

**Why Platform's page, and what cannot be made native.** Connecting is started by the assistant, not by Kitchie: the person adds Kitchie's address in Claude or ChatGPT, the assistant calls `/mcp`, gets a 401 with `resource_metadata` pointing at Platform (`kitchie app.ts:903`, `platform-config.ts:133`), and sends the person to Platform's authorize page (OAuth 2.1, PKCE, the assistant identified by a Client ID Metadata Document, only for hosts on Platform's allow-list, UAT `claude.ai,chatgpt.com`: `oauth-client.ts:6-20`, `docs/runbooks/uat-composition.md:93`). A signed-in person skips sign-in (`server.ts:705-714`, same origin cookie) and sees the consent page (`pages.ts:216-231`: "<name> wants to connect to <product> as <member>", Agree and connect, Cancel). Three hard limits: (1) Kitchie cannot start OAuth toward Claude or ChatGPT; it can only send the person to where the assistant's own connect dialog is. (2) The consent page cannot be framed in Kitchie (`frame-ancestors 'none'`, `server.ts:742`), and an Agree or Cancel redirects to the assistant's own redirect address, not back to Kitchie (`server.ts:759`, `:771`). (3) Platform hosts the page on purpose: it is the authorization server and the assistant has to trust it (the "Platform UAT connect" look is its bare `shell()` page, a `Connect an assistant` title and, in UAT only, the dev-sign-in banner, `pages.ts:57-71`, `server.ts:376-384`). Platform's own rule is "coherence, not concealment" (platform `docs/project-plan.md` D17). What can be done: the page restyled in Kitchie's look with no UAT chrome (Platform's change, SW-O36), the person never sent to Platform's `/connect` list at all, and a waiting state in Kitchie that turns Connected by itself.

**Per assistant.** Claude: documented install link `https://claude.ai/customize/connectors?modal=add-custom-connector&connectorName=NAME&connectorUrl=ENCODED_URL` opens its Add custom connector dialog with name and address filled in, and the person confirms (Anthropic connectors docs, "Share an install link"; Team and Enterprise members connect an Owner-added connector from Customize > Connectors instead). "Open in Claude" is the Plan button's link, `claude.ai/new?q=` (the officially documented prefill is the desktop scheme `claude://claude.ai/new?q=`, support article 14729294; not used because a page cannot tell whether the app is installed). ChatGPT: no documented link that opens its connector dialog or fills it in, none that opens a chat with a message (the `?q=` form is unofficial); the OpenAI docs say to create a custom MCP server from its Plugins page (or Settings, Apps and Connectors, with developer mode, as third-party guides describe), address ending `/mcp`, authentication OAuth; it uses the Client ID Metadata Document `https://chatgpt.com/oauth/client.json` and was refused by Platform until `chatgpt.com` was on the allow-list (`uat-rollout-lessons.md:62-70`). Gemini: unverified that the consumer Gemini app can add a custom connector at all (Gemini Enterprise can); Platform supports only the metadata-document client style (SW-O37). Another assistant: a pasted-in token, no name, no link.
