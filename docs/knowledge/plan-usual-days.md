**Redesigned on the owner's review the same day (17 Oct 2026, voice).** He looked at the first draft and wanted it simpler: no legend, a cell that matches the household is plain, only a cell that differs from the household is marked (a dotted ring), tapping a marked cell again resets it, the phone list is a fixed height showing the household and you with the others scrolling in place, and you change only your own row. This **reverses UD-P5** (an own value equal to the household's is no longer kept) and drops the bulk **Inherit all** (UD-P6). **Words used throughout (UD-D14):** a day is **open** (cooking possible, drawn unfilled) or **off** (not cooking, drawn filled). Against the household a person's day is either **the same as the household** (plain, the default: the person has said nothing) or **different from the household** (a dotted ring). Those are the owner's own words; there is no "inherited", "follows" or "pinned", and no key.

## What the owner asked (Kitchie #860, voice, 17 Oct 2026, with a screenshot of the desktop Plan "Meal planning" flyout, which is now called **Off days**, UD-D13)

1. A **household level** of usual days off cooking that applies to everyone by default, and keep each person's own setting.
2. **The person wins.** Where a person's own setting disagrees with the household's for a weekday, their own setting wins for them, whether it marks a day off the household has open, or opens a day the household has blocked.
3. **Remove the Categories / Leftovers rename row** from this flyout.
4. **Reuse the pattern from the Home cooking-ideas page work** (its personal-versus-household handling and its flyout layout), and keep consistent with `DESIGN.md`, Kitchie `docs/design-principles.md` and the tokens.
5. Mockup first, then build straight into `uat`; no further sign-off rounds on the mockup, judgment calls recorded as numbered decisions and open questions.

## The design

One flyout, one script, two containers: a **right-hand lane flyout on desktop** (1024px and up, UD-P1) and the **bottom sheet on a phone** (and tablet) it has always been. Inside:

1. Title **Off days** (UD-D13), the existing sentence unchanged, an X on desktop (the phone keeps Done at the foot).
2. **HOUSEHOLD · EVERYONE'S DEFAULT**: seven weekday chips (filled = not cooking), then one line ("Off every Tue and Fri."). Editable by household admins; for a member who is not an admin the same row is read-only with "Only household admins can change this." A tap changes it at once and the status line says so, with Undo.
3. **YOU (SAM)**: seven chips that show the **effective result**. A chip that matches the household is plain; a chip that differs carries the dotted ring (UD-D17). One tap flips a day; a tap on a day that already differs puts it back to the household's and the mark goes (UD-D18). One line says how you differ ("Different from the household: Fri open, Sun off.") or that you do not ("Same as the household.").
4. **JANE · ONLY JANE CAN CHANGE** and everyone else: the same chips, read-only, drawn the same way, so you can see where Jane differs.
5. **No legend, key or bulk reset anywhere** (UD-D16).

**Phone (UD-D20):** the sheet's list is a fixed height that shows exactly two rows, Household and You. The other people sit below it in the same box and are reached by scrolling in place; a fade at the foot and the status line ("Jane and Priya below.") say there are more. **Desktop** shows everyone, in the order household, you, the others. The centred-window alternative (`desktop.html?c=dialog`) shows everyone too.

### How a chip is drawn (UD-D16, UD-D17)

The **value** is the fill: **filled = off, unfilled = open**, on every row, as the days have always read. Only one thing is added on top, and only where a person's day **differs from the household's**: a **dotted ring** inside the chip. The household row has no ring (it is the source).

| The household | The person's day | Look | Hover, long-press, focus |
|---|---|---|---|
| open | open (same) | plain unfilled | "Same as household" |
| off | off (same) | plain filled | "Same as household" |
| off | **open** (the person opened it) | **dotted open**: unfilled with the dotted ring | "Different from the household (open). Click again to reset" |
| open | **off** (the person closed it) | **dotted off**: the solid fill with the dotted ring | "Different from the household (off). Click again to reset" |

The ring is a shape, not a colour, and reads on both fills (it takes the chip's text colour). Another person's marked day says "Different from the household (off). Only Jane can change this". Each chip's accessible name says the same ("Friday, open, different from the household, which has it off. Click again to reset"; "Tuesday, not cooking, same as household"). With a household of one and no household days there is nothing to differ from, so no chip is ever marked and none has a tip.

### What the person sees, and what wins

Effective result for a person on a weekday, highest first (UD-D1): a one-week change for that date (`plan_blocks`), then the person's own setting for the weekday (stored only where it differs from the household, UD-D18), then the household's, else open. Examples in the default sample (Tue and Fri are the household's days off): Sam matches Tue (plain, off: "Every week, usual day off, same as household"); Sam opened Fri himself (dotted open; a plain open night in the week); Sam closed Sun himself (dotted off: "Every week, usual day off"); Jane closed Wed (dotted off).

## Build impact (for the build agent)

**Verdict: a no-database-migration encoding exists, but I recommend against it; a schema change (48) is the right shape, and it is small.**

### What the owner's redesign changes in the build (UD-D18, UD-P5 reversed)
The two tables of schema 48 are unchanged (`plan_household_stencil`, `plan_stencil_open`); what changes is the rule for what goes in them: **a personal row exists only where it differs from the household**. Own off exists only on a weekday the household has open (that is today's `plan_stencil`, unchanged for a household with no household days), and own open (`plan_stencil_open`) only on a weekday the household has off. So:
- **Write path (person):** `setStencil` is "set this weekday to off/open for me" and normalises on write: if the value equals the household's, delete both rows for that weekday; else write the matching one and delete the other (a weekday is never in both). The tap in the UI is `PUT {weekdays, open}` computed from the flipped value; resetting is the same call with the value that equals the household's.
- **Write path (household):** the household write (`householdWriteAllowed`) also deletes, in the **same transaction**, every member's `plan_stencil` / `plan_stencil_open` row for that weekday that now equals the new household value. The old design said the household never writes a person's setting (UD-D6); this still holds in effect (no one's effective result changes, the delete only removes a row that has become redundant), but it is a household write that touches person rows, so it goes through the same guarded transaction, is one plan event ("Changed the household's usual days off to Tue, Fri"; the event's detail lists whose rows were dropped) and is undone by Undo (a restore of the previous household list and the dropped rows).
- **Read path:** unchanged (own off, else own open, else household). Rows written by an older client that equal the household are tolerated and read as the same (harmless); a one-off tidy is not needed.
- **Why this is simpler for the person and no costlier for the server:** one value per weekday per person, no "pinned" state, no bulk-clear endpoint. The `known` members query and the removed-member erase are unchanged.
- **Tests to add:** an own value equal to the household is not stored; a household flip drops the matching overrides and nothing else; Undo restores them; a weekday is never in both tables; the week read still returns the effective `stencils[member]`.
Note for the build agent working on #860 in parallel: this reverses the earlier "keep as pinned" proposal (UD-P5) and drops Inherit all; take the stored model from this section. Nothing in Kitchie was touched for the redesign.

### Why a stencil row cannot hold it
`plan_stencil` rows say "off"; no row says nothing. A household layer needs a second set of weekdays, and a person's "open" on a household-off weekday needs a third place, because "same as the household" and "open" would both be "no row". Whole-set override (a non-empty personal list replaces the household's) does not work: a person with no days off who wants Friday open has an empty list, which is the same as "inherited".

### The no-DDL encoding, exactly, and its risks
Rows in the existing tables under values that are not member ids: household days as `plan_stencil` rows with a reserved `member_id` (say `"~household"`), and a personal "open" as `plan_stencil` rows with `member_id = "<member>~open"` (`memberIdOf` accepts any string up to 100 characters, so nothing validates against it). It needs no DDL and no version bump. Risks:

- `planWeek` builds its `members` list from `SELECT DISTINCT member_id FROM plan_stencil` (`plan.ts` about line 1212): both reserved ids would appear as people in the Plan strip, so that read must filter them, and so must every future reader.
- Nothing erases rows keyed by `"<member>~open"` when a member is removed (the removed-members erase works by member id), so personal choices would be left behind after the erase the owner promised.
- The schema stays 47, so **older code runs against the new rows**: after a rollback the phantom people appear and the household days silently stop applying (a household that relied on Fridays off starts planning Fridays). Every earlier bump in `store.ts` (27, 28, 31, 45, 47) takes a version for exactly this reason, even when no DDL changes (27 is JSON in an existing column).
- It overloads a column whose meaning is a person, and the contract tests and fixtures (`server/test/fixtures/schema30.sql`) would have to learn the exception.

### The smallest schema change: schema 48, two new tables, additive, nothing rewritten
Same pattern as 29, 31 and 45 (new tables only, idempotent `CREATE TABLE IF NOT EXISTS`, code older than 48 refuses to start so code and data roll back together):

```sql
CREATE TABLE IF NOT EXISTS plan_household_stencil (
  household_id TEXT NOT NULL,
  weekday INTEGER NOT NULL CHECK (weekday BETWEEN 0 AND 6),
  PRIMARY KEY (household_id, weekday)
);
CREATE TABLE IF NOT EXISTS plan_stencil_open (
  household_id TEXT NOT NULL,
  member_id TEXT NOT NULL,
  weekday INTEGER NOT NULL CHECK (weekday BETWEEN 0 AND 6),
  PRIMARY KEY (household_id, member_id, weekday)
);
```
`plan_stencil` is unchanged and keeps meaning "this person's own off". No data copy, no backfill: with both tables empty every household behaves exactly as today. A weekday must never be in both `plan_stencil` and `plan_stencil_open` for one member: `setStencil` writes both in one transaction, and a read treats off as winning if both ever exist. Why two tables and not a column on `plan_stencil`: an extra column on the table old code reads would make old code treat "open" rows as "off" (the opposite of the truth); new tables are simply ignored by it. The version is **48**; **#838's Option 2 also needs 48** (only that option, which the owner has not picked), and the factory flow allows one schema change at a time, so whichever is built first takes 48 and the other takes 49. The schema slice is a **guarded lane** change (risk package, the owner merges the schema slice). Risk package line: what could silently change is the blocked nights of every member who has not set their own, once an admin sets household days; until then nothing changes.
