Recipe photos

Draft for feedback, one slice of the Recipe tab (gap G7). Two halves: the architecture decisions to lock before anything is built (where the bytes live, sizes, uploads from the app and from an assistant, limits, versions, privacy, caching, deletion, backups), and a clickable phone mockup of the experience. Storage is not drawn: only what a person sees. Everything is a Proposal until the owner says yay, nay or combine.

Reconciled 10 October 2026 with the other Recipe tab slices: the versions spec now carries photo_ids on a cook and cover_photo_id on a version, as P-D4 and P-D13 say; the remove rule (P-D17) meets the preferences admin role and stays open. Build handoff: recipe-tab-handoff.md. Nothing has been built or filed.

Try it

Every screen is a live phone. Mockup (bottom right) switches between Has photos, No photos yet and Slow network, and shows what that screen has loaded so far.

On the recipe page, tap any photo to open it (Replace cover, Use as cover, Remove). Remove has Undo, and a "Delete it for good now" for a photo that should never have been added.

Options for yay, nay or combine

Where the choice is real, each option is written with its downside. The recommendation is marked; the downside of the recommendation is said plainly.

P1Who owns the photos (P-D1)

A Recipe owns them. Bytes and their records live with Recipe's data; Kitchie only shows them by id. Matches "each app keeps its own persistence".

B A shared photo service in Platform for every product.

C Kitchie stores them, since Kitchie is the only screen.

Recommended A

Downside of A: Recipe, which today serves only JSON, gains a route that serves files and a folder that grows. If Kitchie later wants item photos it builds the same thing again for itself (B avoids that, at the cost of a new shared service everyone depends on).

P2Where the bytes sit on the server (P-D2)

A Files in a photos/ folder next to recipes.db, inside Recipe's existing data folder; the database holds one small row per photo.

B Inside SQLite as blobs in recipes.db. One file, always consistent.

C Tencent object storage (COS). Unlimited, off the server.

Recommended A

Downside of A: two things to keep in step (a row and its files). Handled by writing files first and the row second, and a nightly sweep for strays. B makes every database backup copy every photo again and bloats the database the app reads all day; C is a metered service, which breaks "pays for nothing".

P3What is kept per photo (P-D6)

A Three WebP sizes, no original: large 1600px (viewer), medium 960px (top of the page), square 240px (lists and galleries), plus a colour and a 24px blurred preview stored in the row.

B A plus the phone's original (3 to 6 MB each).

C Original only, resized on request.

Recommended A

Downside of A: the full-quality original is gone; a print or a much bigger screen later cannot get more detail than 1600px. B costs about 15 times the disk; C makes the 2 vCPU server resize on every view.

P4Who shrinks the photo (P-D7)

A The phone. Kitchie's add screen makes the three sizes in the browser before sending; Recipe checks them and stores. No image library on the server.

B The server with an image library (sharp/libvips).

C Both: the phone shrinks to 1600px, the server makes the other two.

Recommended A

Downside of A: the server has to trust bytes it did not make, so it checks strictly (real WebP, sizes and dimensions within caps) and cannot fetch and shrink a photo from a web link by itself (option 5C needs B or C). B adds a native dependency, a bigger container and CPU spikes on a small server.

P5How an assistant adds a photo (P-D12)

A A one-time add link. The assistant calls request_photo_upload; the person taps the link and picks the photo in Kitchie, already aimed at the right recipe and cook. No picture goes through the chat.

B Picture data in the tool call (base64).

C A web address: the assistant passes an image URL (e.g. from a recipe page) and Recipe fetches it.

Recommended A now; C later, for drafts only

Downside of A: one more tap for the person, and the assistant never sees the photo it "added". B is huge in tokens, capped by every assistant, and lets an assistant store any image without a person looking. C is a server that fetches addresses it is told to, which must be fenced off from the private network, and needs option 4B or 4C.

P6What a photo is attached to (P-D9)

A A version (its photos and one cover), or a cook (cooked-it photos). A version with no cover shows its parent's, labelled "Photo of With peas".

B The recipe as a whole: one gallery and one cover for every version.

C A revision: every fix keeps its own photos.

Recommended A

Downside of A: a new version that looks quite different still shows its parent's photo until someone adds one (the label says so). B shows the wrong dish for a version that changed a lot; C makes a photo vanish after a typo fix.

P7When nothing has a cover (P-D10)

A The parent's cover, then the newest cooked photo, labelled with its date; any photo can be made the cover with one tap.

B Only recipe photos can be covers; a cooked photo never leads.

C No covers: the newest photo of any kind leads.

Recommended A

Downside of A: a dark, messy dinner-table photo can become the face of the recipe without anyone choosing it. The date label tells everyone it is "what we made", not the ideal.

P8Who can see a photo (P-D15)

A Same-site, signed-in only. Images are plain addresses under /recipe/photos/… on the same site; Recipe checks the Platform sign-in cookie and the household on every request. No public links, no token in any address.

B Signed links that expire after an hour.

C Loaded by script with the token, shown as in-memory images.

Recommended A

Downside of A: it only works while Kitchie and Recipe are on one site (true today: one edge, path prefixes). An assistant cannot fetch a photo; nobody can share a photo link outside the household (by design). B links leak through copy and paste until they expire and change every hour, which defeats the browser cache; C defeats lazy loading and the cache.

P9Limits (P-D8)

A Tight: 6 recipe photos per version, 3 per cook, 1 MB per upload after shrinking, 2 GB per household, 60 uploads an hour per member.

B Roomy: 20 per version, 10 per cook, 5 GB per household.

C Only a household total.

Recommended A

Downside of A: someone who photographs every stage of a cook hits 3 quickly (step photos are a later piece). The caps are settings, so raising one is a config change, not a migration.

P10Removing a photo (P-D17)

A Hidden at once, gone for good after 30 days, with Undo and a "Removed photos" list; plus "Delete it for good now" for a photo that should never have been there.

B Gone at once, Undo for a few seconds only.

C Never deleted, like recipes.

Recommended A

Downside of A: the file stays on the server for 30 days, and in backups until they roll over, even though nobody can see it. C is not acceptable for photos: they can show people and homes.

P11Backups (P-D18)

A Same backup as the database: the photo folder is inside Recipe's data folder, so today's backup already includes it.

B Database as today, photos copied as new files only (a photo's file never changes, so only new ones are copied).

C No photo backups.

Recommended A now, B past about 500 MB

Downside of A: every backup copies every photo again, so backups grow quickly. Both A and B still sit on the same server: a lost disk loses both. Getting a copy off the server is an open question for infra, not this slice.

P12Photo at the top of the recipe page (P-D20)

A Full width, 195px tall, swipe for the version's other photos. Only the cover loads; the rest on first swipe.

B Small square beside the title (72px). Ingredients start 180px higher.

C None at the top; photos only in the Photos section.

Recommended A

Downside of A: ingredients start lower, and it is the biggest download on the page (one medium photo, about 60 to 90 KB). B is the pick if the page is used more to cook from than to choose.

P13Photos in the list (P-D21)

A The cover in the existing 56px tile, instead of the emoji. No row grows.

B No photos in lists: emoji only, nothing downloaded.

C A smaller 40px thumbnail and slimmer rows: more rows per screen.

Recommended A

Downside of A: each row on screen downloads a small thumbnail (about 10 to 15 KB). B is the zero-cost choice if the list is used mostly by searching.

Decisions in this slice (P-D numbering, all Proposal)

The same list is appended to docs/knowledge/jobs-to-be-done/recipe-tab.md.

  1. P-D1Recipe owns recipe photos; Kitchie stores none and shows them by id. Each app keeps its own persistence; across apps only ids and the contract in P-D5 travel. Option P1. Proposal
  2. P-D2Files in photos/ beside recipes.db, in Recipe's data folder (today the recipe-data volume; if Recipe moves to a /home folder like Kitchie, photos move with it, since snap Docker can only bind-mount under /home). Folder per household, file per photo and size: photos/<household>/<id>-t.webp. Option P2. Proposal
  3. P-D3Disk budget. About 350 KB per photo for all three sizes, so 1,000 photos is about 350 MB. A household cap (P-D8) keeps one household from filling the server. Check the server's free space before turning photos on (df -h on the data folder); the Lighthouse disk size is not recorded anywhere this slice could read. Proposal
  4. P-D4One row per photo in Recipe's database: random 128-bit id (never a counter, so ids cannot be guessed), household, recipe family, version or cook, kind (dish or cooked), who added it and through which channel (app or assistant), width, height, the square crop, colour, the 24px preview, bytes per size, added, removed, purge after, and for a web photo the page it came from. A version gets one changeable pointer, cover_photo_id (fits the versions slice's V-D16 list of what may change). Proposal
  5. P-D5The contract. Recipe's responses carry photo ids plus colour (and the preview for the cover only); never bytes. HTTP: GET /recipe/photos/<id>/t|m|l.webp, POST /recipe/photos (the three sizes and the target), remove and restore. MCP: request_photo_upload (P-D12) and photo ids in recipe and cook replies. No picture bytes ever go through MCP. Proposal
  6. P-D6Three WebP sizes, no original: l 1600px long edge, m 960px, t 240px square crop; quality about 75. WebP works in every browser Kitchie supports. Colour and preview are computed once and stored. Option P3. Proposal
  7. P-D7The phone makes the sizes. Re-drawing the photo in the browser also drops its location and camera data. Recipe accepts only WebP with the right dimensions and size, and rejects anything else. Option P4. Proposal
  8. P-D8Limits: 6 recipe photos per version, 3 per cook, 1 MB per upload, 2 GB per household (a slim line warns at 80%), 60 uploads an hour per member. All are settings. Option P9. Proposal
  9. P-D9Photos belong to a version or to a cook, never to a revision. A fix to a version keeps its photos. A new version starts with none and shows its parent's cover, labelled. A spin-off (V-D25) offers "Bring the cover along" (on by default), which copies the files so the two recipes never share bytes. The Photos section on the page shows the whole family's photos, this version's first. Option P6. Proposal
  10. P-D10Cover: the first recipe photo of a version becomes its cover; any photo, cooked ones included, can be made the cover with one tap. With no cover up the line, the newest cooked photo stands in, labelled with its date. Option P7. Proposal
  11. P-D11Adding from the app: the camera icon in the recipe page's top row, the Add tile in Photos, and the end of a cook (R-D19). The phone's own camera or picker; then one question, "What is it?": Tonight's cook (default) or Cover of this version, with a square crop for a cover; an optional line for a cook. Up to 3 at once from one cook. Sending shows progress, carries on in the background and retries. Proposal
  12. P-D12From an assistant: a one-time add link (15 minutes, one use, bound to the household and the target) that opens Kitchie's add screen already aimed; the person picks the photo. Later, for a recipe the assistant drafts from a web page, it may pass the page's photo address; Recipe fetches it (https only, public addresses only, 8 MB, images only) and Check it shows it, so a person still keeps or drops it. Option P5. Proposal
  13. P-D13Cooked-it photos are part of the cook entry (gap G2, the versions slice's record_cook with up to 3 photo ids). Spec aligned: photo_ids They show as a thumbnail on that night's row in Cooked and in Photos with date and who. They are not the cover unless someone chooses it, or nothing else exists (P-D10). Proposal
  14. P-D14Nothing jumps, nothing loads early. Every photo box has its size before a byte arrives and is filled with the photo's own colour (no request). Thumbnails load only when within 200px of the screen. The top photo on the recipe page is the only photo loaded up front, with the 24px blurred preview inline so something appears at once. Its siblings load on first swipe. The large size loads only in the viewer, only for the photo opened. The add screen and its shrinking code are a separate route. Proposal
  15. P-D15Private to the household. Same-site addresses checked against the Platform sign-in cookie and household on every request (verified locally, platform D11); 404 for anyone else, the same answer as "no such photo". No public URLs, no tokens in addresses (so nothing sensitive lands in the edge's access log). Option P8. Proposal
  16. P-D16Caching: a photo's bytes never change (replacing makes a new photo with a new id), so the browser keeps them for a year, privately (private, max-age=31536000, immutable). Nothing is shared through a public cache. A removed photo stops being listed at once; a device that already has it keeps its copy until the browser drops it. Proposal
  17. P-D17Removing: by whoever added it or a household admin (preferences D25 to D30; in a household without admins, any member except a follower). Hidden at once with Undo, restorable from Removed photos for 30 days, then the files are deleted and the row keeps only that a photo was removed, by whom and when. "Delete it for good now" skips the 30 days. Removing the cover falls back as P-D10. A household that leaves takes all its photos with it. Option P10. Proposal Open X3, X6: under D26 every household has an admin, and "follower" is not a stored role
  18. P-D18Backups: the existing backup of Recipe's data folder includes photos (option P11 A). Order matters: database first, then photos, so every photo the backup's database names is in it (files are only deleted 30 days after removal). Move to copying only new photo files once photos pass about 500 MB. Proposal
  19. P-D19No photo, no pretend photo. No grey box on the page or in the list: the recipe's emoji sits in the tile and beside the title (R-D9 stands). Photos shows one dashed line, "No photos yet: snap it next time you cook it", with one tap to add. Proposal
  20. P-D20Top of the recipe page: option P12. Either way a version with an inherited photo says whose it is. Proposal
  21. P-D21Lists: option P13. The same 240px square is used for every thumbnail in the app (lists, Cooked, Photos, the Versions sheet, Plan), so one file serves them all. Proposal
  22. P-D22Viewer: tap a photo to see it large, with who and when; Replace cover or Use as cover; Remove only for those allowed (others see who can). Proposal
  23. P-D23Step photos later. Same mechanism with kind step and a step number; not in the first build. Proposal
  24. P-D24A photo from someone else's website is stored for the household only, with the page it came from, and is never shown outside the household. Proposal
How a photo travels
1Pick. Phone camera or library, in Kitchie's add screen (a route of its own).
2Shrink on the phone. 1600, 960 and a 240 square, WebP; location data gone. A 4 MB photo becomes about 350 KB in all.
3Send to Recipe on the same site with the sign-in cookie. Recipe checks household, limits and that the files are real WebP of the right size.
4Store. Files into photos/<household>/, then the row. Colour and preview kept in the row.
5Show. Lists get the id and colour; the page gets the cover's preview too. The browser fetches the square or medium size only when it is about to be seen, and keeps it.

Open questions
  • Server disk: how much is free on the data folder? A wrong guess could fill the server; P-D8's household cap is the guard.
  • An off-server copy of backups (for all apps, not just photos): is any included in the current Tencent plan at no cost? Infra's call.
  • Option P4 against option 5C: choosing A (phone shrinks) means a web photo for a draft has to wait for a server image library.
  • Can a follower add a cooked photo? Mockup: yes (R-D8 says star, notes and photos stay); they cannot remove other people's.
  • Does replacing a cover keep the old one in Photos (mockup) or remove it?
  • Are Recipe and Kitchie always served from one site? Option P8 A depends on it; a separate subdomain later would need option P8 B.
