1. Rules (replace "recipes and variations are immutable")
  1. BR1 Revisions are immutable. Locked 5 A A revision's change set, author, channel, words and time never change and are never deleted (DB triggers, as today's recipes_immutable). The objects a revision points at are content-addressed and immutable too (BR14).
  2. BR2 Versions and families are changeable pointers. Locked 5 A Allowed to change: version name, state, head_revision_id, notes_head_id and photos_head_id (9.4, 9.5; they only move forward), cover_photo_id (P-D4), dismissed_by; family name, usual_version_id, put_away. Each member's own reaction (BR19). Nothing else. Every change appends a journal event with actor and channel.
  3. BR3 Nothing a person made is deleted. Locked (owner, typed, 10 Oct 2026) Put away (state = put_away) replaces disabled. No DELETE on families, versions, revisions, notes, cooks, reactions, reviews, and no delete tool, not even for a try made by mistake: that try is put away, with undo. Owner: "UNDO is needed, this is why I want you to be efficient in storage of diffs." The only things ever removed are unreferenced objects (9.9) and photo files, which are the photos slice's (P-D17; the free-space flow, 9.5). Keeping a mistake costs about 1 to 2 KB (9.10). Replaces: "Open: hard delete of a try made by mistake; build default none".
  4. BR4 One usual per family, always. It must be a version in state trying or kept. Setting a trying version as usual also sets it kept. The usual cannot be put away until another is the usual.
  5. BR5 Parent is pinned. A version records parent_version_id and parent_revision_id. Later revisions of the parent never change the child. "Bring in the parent's fix" is a normal revise by the caller. (With 6 B this matters more: a child's first revision is a change set against a pinned parent revision, and a pinned revision never moves.)
  6. BR6 Optimistic concurrency. Every write to content names base_revision_id. If it is not the head the server never overwrites: it rebases when the two change sets touch different items, else it fails with stale_base (section 9.8).
  7. BR7 Author, channel and client on every write. actor_member_id from the session (platform token; legacy in standalone); channel app (HTTP from Kitchie) or assistant (MCP); client the MCP client's name from the session handshake (e.g. "Claude"), for "which assistant". Set by the server; the caller cannot.
  8. BR8 Assistant writes carry the person's words. On channel assistant, user_intent is required on every content or state write. On app it is optional (the tap is the intent). Same "never paraphrase into approval" wording as today's create_variation.
  9. BR9 Assistant scope. Locked 4 B On channel assistant, with the person's words: create recipes (born suggested) and versions (born trying); revise any version, kept versions and the usual included; set state, set the usual, put away, spin off, rename, write notes. A revise of a kept version or the usual by an assistant opens a review (BR15). Not allowed to an assistant: resolve a review, accept its own draft (Suggested → Trying needs a person in the app or the person's words saying yes, BR10). Not chosen: 4 A suggest only (needs_person on a kept version; propose_change and suggestions removed), 4 C trusted per member (assistant_trusted removed).
  10. BR10 Suggested is invisible to ordinary reads. A family whose only version is suggested is a draft (R-D12, gap G3): excluded from list, search, what_can_i_cook and ideas unless include_suggested. Accepting it (the app, or the person's own words through their assistant: "yes, add it") moves it to trying. Dismissed (Not for us on a draft) sets state = put_away with dismissed_by: it is then visible only in that member's assistant history (list_my_drafts for the member who made it, through their assistant), never under the household's Put away, never in lists or search. Undoable by that member at any time (accept or bring back). Locked (owner, typed, 10 Oct 2026) Replaces: "Open: how long dismissed drafts stay visible; default in the member's assistant history only, a put-away draft shows under Put away".
  11. BR11 Temporary substitutions are still not persisted. "I used pork tonight" is a cook-log line, not a revision, unless the person says keep it.
  12. BR12 Missing stays missing. basis, value: null, no invented servings, times or amounts. Unknown is a real value and diffs like one.
  13. BR13 Reasoning stays with the caller. The server never picks a version, never judges a substitution, never decides a try is good, never fetches a link or reads a photo (L4).
  14. BR14 Changes only, git-like. Locked 6 B A revision stores a parent pointer and a small structured change set; content lives in content-addressed immutable objects; checkpoints bound rebuild cost. Section 9.
  15. BR15 Review after, for kept versions. Locked 4 B Any assistant revision on a kept version or the usual creates one open review row listing its changes. The change is live at once. Any member (L5) can accept all, or revert one change (a new revision that reverses exactly that change, section 9.6). The review stays open until every change is accepted or reverted. A cook meanwhile is logged against the revision it used; the review is not closed by cooking. Tries are never reviewed.
  16. BR16 Everyone is equal. Locked L5, L8 No Recipe write is gated on a household role: making, fixing, keeping, putting away (whoever cooked it), changing the usual, removing photos, resolving reviews. not_allowed remains only for app-only tools called on the assistant channel. Authorship is still recorded on every write for attribution. Supersedes V-D23's admin rule and the old set_usual admin check.
  17. BR17 "Not for us" after a try's first cook puts it away at once. Locked (owner, typed, 10 Oct 2026) record_cook with verdict: "no" on a trying version sets put_away in the same transaction, from the first cook, and returns undo: {event_id}; the app shows Undo in the toast and Bring back stays on the version for ever (BR18). The usual cannot be put away (BR4): the verdict is logged and the state is left, with is_usual as a warning. Replaces: "Open: at once or wait for a second cook; build default at once".
  18. BR18 Undo any time, never a rewind. Locked (owner, typed, 10 Oct 2026) Every content change can be undone (revert_change, restore_revision: a new revision) and every state or pointer change can be undone (undo_event: a new journal event that sets the previous value, provided the value is still the one the event set, else stale_base). No time limit, no "undo window"; the head and the journal only move forward. An undo can itself be undone.
  19. BR19 Reactions are per member; the household's view is derived. Locked (owner, typed, 10 Oct 2026) Owner: "both depending on the situation: if something was cooked it's possible everyone liked it or only some." Each member has their own reaction to a version (liked or no; skip stores nothing), changeable any time, given after a cook or from the recipe page. "Starred" is that member's liked. The household level is never stored as a vote: "liked by 2 of 3", "household favourite" and the Starred filter are computed from the reactions and the cook log (2.1). Replaces: V-D6's "Open, cross-feature X5" and R-V9's "household-wide until X5". Settles X5 for Recipe's side as "both, derived".

Option 5, not chosen: B mutable rows with only the journal as history; C keep today's rule and add only states and the usual.

2.1 The household's view is derived (BR19) Locked 5

  • Liked by: the members whose current reaction is liked, shown by name to everyone ("Liked by Sam and Jane"). Of: the members recorded as eating it in any cook of that version (ate_json), so "2 of 3 who ate it".
  • Not for me: shown by name only to the member who gave it ("not for you"); everyone else sees a count ("1 not keen"). Private to who gave it, visible as a count.
  • Household favourite Rule confirmed (owner, voice, 11 Oct 2026): a version is a household favourite when more than half of the members who ate it liked it, and at least 2 liked it (1 in a one-member household). It is a household setting (favourite_rule: majority | anyone | everyone, default majority), so a household can choose "anyone liked it" or "everyone who ate it liked it". Computed on read; nothing is stored.
  • Starred filter (R-D5): "Liked by me" for the member, and "Household favourites" for the household. Nothing ranks on another member's private "no".
  • After a cook: the end-of-cook asks each member who ate it (the cook records who; prefilled from who usually eats, editable): liked, not for me, or skip. The cook's verdict (Keep it, Needs work, Not for us, BR17) is a separate thing: the household's word on a try's state. A member who taps Keep it is prefilled as liked and Not for us as not for me; they can change it.

What remains for the preferences feature (not edited here): its F1, Q1 and Q-R8 draw Recipe stars household-wide; they should read "per member reactions, household view derived" from Recipe, and decide whether its own person and household preference model (D25 to D30) shows "liked by" on Plan and Ideas, and whether a member's private "no" may lower a recipe's rank in that member's own Ideas only. Cross-feature X5 can be closed for Recipe's side.

Nutrition: nutrition_observations.target_kind gains 'revision'. get_nutrition on a version reads the head revision's figures, else the latest earlier revision's with for_revision and stale: true (V-D29). Nothing recomputed.

Option 6, not chosen: A the whole resolved recipe stored in every revision. It is simpler to read but costs about 4 times the space (section 9.10) and stores every note and every unchanged line again on every save, which is what the owner asked not to do.

4. Errors

Same shape as today, Error [code]: message. hint, with hints written for an assistant.

  • not_found, invalid, conflict, internal: unchanged.
  • stale_base: base_revision_id is not the head and the changes overlap (9.8). Returns {head_revision_id, n, actor, client, created_at, overlapping: [item ids]}. Hint: read the head with get_version, tell the person who changed what, retry on the new base only if they say so.
  • bad_transition: the state move is not allowed (e.g. suggested → kept). Lists the allowed moves.
  • is_usual: cannot put away or spin off the usual. Hint: set_usual on another version first.
  • no_change: the patch produced identical content. Nothing saved.
  • intent_required: assistant channel without user_intent (BR8).
  • target_required: an assistant patch to a kept version or the usual without target. Hint: ask the person "fix this one, keep both, or a different dish?" (pick 2 C) and pass their answer.
  • invented_value: a quantity or time with basis: unknown and a non-null value, or basis: observed with no source text. Hint: unknown stays null.
  • duplicate_key: an idempotency_key reused with a different body. (Same key, same body returns the first result, not an error.)
  • not_allowed: an app-only tool on the assistant channel (resolve_review). Never a household-role check (BR16).
  • too_large: patch over 200 ops, one note over 4,000 characters of text (the only note cap, in the app as well) or a version's own notes over 16 KB in total (10.6), provenance text over 64 KB, import over 25 recipes.
  • invalid_change: unknown item id, bad after, id collision; same as today's resolve.ts.

7. Migration of today's immutable data (v5 → v6), no data loss
  1. Back up first (infra runbook) and run on a copy in UAT; new tables only; v5 tables kept read-only for one release.
  2. Each recipes row → one family + version "Original" + revision 1 (kind migrated, depth 0, a checkpoint). Its ingredients and steps become objects (their existing ids are kept: today's ids are already unique per family, which is exactly the stable item id 6 B needs). Scalars, metadata, tags and source go into the tree. Actor legacy; channel assistant if source.kind is conversation else app. State kept if active, put_away if disabled. It is the usual.
  3. Each variations row (oldest first) → a version in its root's family, name = title or "Version n". Its revision 1's change set is today's stored changes_json mapped op for op (9.3), parent = its parent's revision 1, user_intent and note copied. Variations are already sparse change sets, so 6 B needs no re-diffing: the migration is a mapping, and resolve() of the new chain is tested equal to today's resolveChain() for every variation. A checkpoint is written for every migrated version (cheap, and it makes the head readable without walking old chains).
  4. A disabled root with active variations: the usual becomes the most-used active variation (times_used, then newest); if none is active, the root stays the usual and the whole family is put away. Owner to confirm.
  5. preferences → reactions of the legacy member keyed by version (starred or vote up → liked, vote down → no); times_used/last_used become synthetic cook rows marked migrated with no ate_json. There are no notes today (G1 is not built), so nothing to migrate for 9.4.
  6. nutrition_observations → re-pointed through legacy_ids to revision 1 (append a mapping, never update rows).
  7. legacy_ids for every old id, so old ids in plans, chats and Kitchie keep resolving.
  8. Journal: one migration.v6 event per family with counts and the hash of each migrated head. Test from a real v5 file database at each shape (root only, chain of three, disabled root, disabled middle, nutrition attached), run twice (idempotent).
  9. Rollback: drop v6 tables; v5 tables were not written. After the owner removes the aliases, v5 tables can be archived into the export (9.11).

9. Revision storage: changes only, git-like Locked 6 B Proposal: design

The owner's words (typed, 10 October 2026): "I need something like git in concept where only the change / diff is kept... if you need to transform the persistence layer/method go for it... but it needs to be able to somehow keep rich text, notes, images, links and diffs of things in a storage efficient way."

In one paragraph. Content is cut into small immutable pieces (one ingredient, one step, one note block), each stored once under the hash of its content. A version's content at any moment is a small tree: the scalars plus ordered lists of piece hashes. A revision stores only its parent and a change set of a few structured operations by stable item id; every 10th revision of a version also stores the tree hash (a checkpoint), so rebuilding any revision applies at most 9 change sets to a checkpoint. Photos are files owned by the photos slice and are only ever referenced by id. Everything stays in Recipe's one SQLite file.

9.1 Object model

  • Object = (hash, kind, data). data is canonical JSON (sorted keys, no whitespace, numbers as written); hash is a hash of kind + "\n" + data. Writing an object that exists is a no-op. Objects never change. Kinds: ingredient, step, block (one rich-text block of a note), tree (one version's content at a checkpoint), text (a long provenance text, stored once).
  • Item ids are stable and are not hashes. Each ingredient and step has an id (i7, s3; today's ids are already unique per family) that survives edits. The tree maps position → (item id, object hash). The id says "the same line"; the hash says "its current wording". That split is what makes reorder, insert and delete tiny and what makes blame and three-way rebase possible.
  • Tree = {title, servings, prep_minutes, cook_minutes, tags[], metadata{}, source_hash, ingredients: [[id, hash]...], steps: [[id, hash]...], photo_refs?: none}. About 1.1 KB for a 12-ingredient, 8-step recipe.
  • Revision = (id, parent_revision_id, change_set, tree_hash?, depth, author, channel, client, words, time). parent_revision_id is the previous revision of the same version; for a version's first revision it is the pinned revision of its parent version (BR5), so a new version costs one change set, not a copy.
  • Lines. A version has up to three revision lines in the same table, told apart by line: content (the recipe, everything above), notes (9.4) and photos (9.5). Each has its own head and its own checkpoints; a note or photo change never creates a content revision or a review.
  • Ref = a changeable name to a hash or revision: a version's content, notes and photos heads. Refs are just the changeable columns of versions and families (BR2); the refs view exists for export and gc.

9.2 Checkpoints and rebuild cost

To read a revision: walk back to the nearest revision with a tree_hash, load that tree, apply the change sets forward. A version's first revision whose parent is in another version follows the pin into the parent version; the walk is bounded by depth, which counts change sets since the last checkpoint across the pin, so a child of a child never becomes a long chain.

  • Rule: write a checkpoint when depth would reach K = 10, on every restore, on every migrated revision, and on every spin-off's first revision. So rebuilding any revision applies at most 9 change sets, 4.5 on average, each a few hundred bytes, all from one indexed range read. Measured on a 3.9 KB recipe: well under a millisecond in node; the head itself is served from head_cache, so the common path (open a recipe, cook, plan) applies none.
  • Cost of a checkpoint: one new tree object (~1.1 KB) per K revisions; unchanged ingredient and step objects are shared, never copied.
Sub-option S1: checkpoint interval. K1 every revision (each revision stores its tree; rebuild is one lookup; +30 MB for the household below, and it is really option 6 A with sharing). K10 (as above). K50 (smaller, up to 49 change sets per read; history pages slow down for heavily edited versions). Pick: K10. Downside: two code paths (checkpoint or not) and a property test to keep them equal; K is a constant, so changing it later needs no migration.

9.6 Revert and restore are new revisions

  • Restore (Go back to revision n): the server rebuilds n, diffs it against the head by item id, and writes that diff as a new revision of kind restore, with a checkpoint. History moves forward; nothing is rewound.
  • Revert one change (review, pick 4 B): every op in a change set has an index; revert_change computes the inverse of that op against the current head (an ing.update inverse sets the old field values; a step.text splice inverts to the opposite splice; an add inverts to a remove) and writes it as a new revision of kind revert with reverts = {revision, change ids}. If a later revision already changed the same item, the inverse would clobber it: the call fails with stale_base listing the item, and the review screen says "changed again since; open History".
  • Undo a whole revision (History, "Undo this change"): revert_change with every change id of that revision. Same rules.
  • Undo a state or pointer change (BR18): put away, bring back, the usual, a rename, a banner: undo_event writes a new journal event setting the previous value. A mistaken try is "put away, with undo": the mockup's History lists state changes with their undo (put away try).
  • No time limit, no delete. Every undo is itself a revision or an event, so it can be undone too. The cost of keeping everything undoable is in 9.10.

9.7 Compare, blame and "what the assistant did"

  • Compare two versions or revisions: rebuild both trees; ingredients and steps are compared by item id and hash, so equal objects are skipped without reading them. Output rows like V-D14.
  • Blame ("who changed this line"): walk back from the head to the item's last op; the walk stops at the first revision that touched it, at most one checkpoint interval per hop. For a step with word splices, blame can go down to words; the UI shows the line level (history.html, "Who changed what").
  • What the assistant did: list_revisions filtered by channel = assistant and/or client; each revision shows member, client ("Alex's assistant, Claude"), the person's words and the change set as diff rows. Reviews (BR15) are this filter plus a state per change.

9.8 Two saves at once: parent pinned, never overwritten

Every content write names base_revision_id (BR6). Inside one SQLite write transaction:

  1. If the base is the head: append.
  2. If not: collect the item ids touched since the base. If the new change set touches none of them (e.g. Jane fixed an amount, Alex's assistant reworded step 5), the server rebases: writes the new change set on the current head (its ops are by id, so they apply unchanged), kind rebase, and returns rebased_from. Both edits survive.
  3. If they overlap on an item (both changed step 4): nothing is saved; stale_base returns the head and the overlapping ids. The app shows "Jane saved a change 2 minutes ago" with both (V-D24); an assistant tells the person and retries only on their word.

Text splices inside the same step are never merged automatically. SQLite's single writer makes the check and the append atomic.

9.9 Compaction and garbage collection

  • Never deleted: revisions (all three lines), change sets, checkpoints' trees, objects reachable from any revision, cooks, reactions, reviews, the journal, put-away and dismissed versions. That is the audit trail (V-D15) and what makes undo possible at any time (BR18).
  • Can become unreferenced: objects written by a failed transaction or a dry run that slipped through, a head_cache row, a photo's blobs once its 5-minute undo has passed (P-D17 B, locked; no 30-day restore) and no other photo row in the household has the same hash, an upload in uploads/ once its kept sizes exist.
  • Nightly gc: mark every object reachable from every revision's tree or change set, every notes line, and every review; delete unmarked objects older than 7 days (the retention window, so an in-flight write is never collected). The photos slice's blob sweep (RP1: stray blobs with no row, removals past their 5 minutes) runs in the same nightly job, database first, then blobs, through the BlobStore port (listByOwner, delete). A removal's blobs may also be deleted as soon as its 5 minutes pass; the nightly sweep only catches what that missed.
  • Compaction: optional and rare. A long-lived version's old checkpoints can be thinned (keep every 5th) because rebuild still works from an earlier one; never needed at the sizes below. VACUUM monthly.

Reading it: both models fit the 2 GB budget easily; photos, not recipes, are what fill a disk. 6 B is about 4× smaller than 6 A (still ~1.3× smaller than compressed snapshots), and, more usefully, its cost grows with how much people change, not with how big the recipe is, so long notes and big recipes edited often stay cheap. Worst case for 6 B: a version rewritten wholesale on every save degrades to roughly 6 A plus ~10%.

9.12 The persistence method: what changes, what it costs, what it buys

Stay in SQLite (node:sqlite, as today), with the tables in section 2. No new service, no git binary, no object store.

Sub-option S3: where objects live. SQLite table (objects, as above): one file, transactional with revisions, today's backup covers it. Files (a objects/ab/cdef… tree like git): easy to inspect, but two things to keep consistent and many small files. A real git repository per household (libgit2 or the git CLI): proven tools, but git diffs lines of text, not ingredients by id; rich text and structured quantities would need a text encoding; and the server gains a native dependency. Pick: SQLite table. Downside: not browsable with git tools; the export (9.11) covers that need. Large blobs never come here (photos are hash-keyed files behind the photos slice's blob port), so SQLite's sweet spot of small rows holds.

What it costs to change. Schema v6 and its migration (needed by 5 A anyway); a new store/objects.ts (put, get, canonical JSON, hash); resolve.ts grows from 7 ops to about 20 and gains inverses; a word diff routine; checkpoint and rebase logic; property tests (rebuild = cache, inverse ∘ op = identity, migration = today's resolveChain). Roughly one large slice plus one small one (R-V2, R-V11), on top of 5 A's work. Every read of a head goes through a cache, so read paths stay as fast as today.

What it buys. About 4× less space for recipe history and a cost that tracks edits; rich-text notes with per-block history; blame and per-change revert (which pick 4 B's review needs: "undo this one change" is an inverse op, not a whole-recipe restore); automatic rebase of non-overlapping concurrent saves; a direct, lossless migration from today's variations, which are already sparse change sets.

10.1 Rules the descriptions teach

  1. The assistant brings the text. Recipe never fetches a link, reads a photo or scrapes a page. If the person shows the assistant a card, a page or a voice note, the assistant reads it in its own app and passes structured content and the provenance text. source.reference may hold a URL as plain text; it is never opened.
  2. Ask, never invent. Unknown amounts are {value: null, basis: "unknown"}; unknown servings or times are omitted. basis says how each value was obtained: observed (read from what the person showed), entered (the person said it), inferred (the assistant's guess: allowed only when the person accepts a guess, and shown as such). Ask the person one short question when a missing value changes what they do (a quantity for the main ingredient); otherwise leave it unknown.
  3. Suggested on create. A recipe made by an assistant is a draft until a person says yes (BR10). If the person has already said "save it" in the chat, the assistant may call accept_suggested with those words.
  4. Say where a change lands (pick 2 C). On a try: fix it in place. On a keeper or our usual: ask "fix this one, keep both, or is it a different dish now?" and pass the answer as target. Then tell the person what happened, and for a keeper that the household will see it as "To review" (pick 4 B).
  5. Show duplicates, never merge. Same as today.
  6. Pin and retry safely. Every edit names base_revision_id from the last read and an idempotency_key; a retry with the same key returns the first result.
  7. Temporary is not saved (BR11); "just tonight" goes into record_cook.line.

10.5 Duplicates, idempotency and bulk

  • Duplicates: as today's duplicates.ts (title, ingredient overlap; score 0..1 with reasons), returned by validate, create and import. Never merged. A duplicate draft can be dismissed by the person (it then shows only in their assistant history, BR10), never deleted.
  • Idempotency: every write takes an idempotency_key (client-made, up to 80 chars), unique per household for 30 days. Same key + same body returns the stored result; same key + different body is duplicate_key. Chat clients retry on timeouts; this makes a retry safe.
  • Bulk: import_recipes up to 25 per call; rate-limited with the rest of the MCP boundary.

10.6 Data limits

Same zod boundary as domain.ts: 200 ingredients and 200 steps, strings to 4000 characters, provenance text 64 KB (a text object, stored once, never shown in the app), 200 ops per patch. Notes as below.

Note length: one cap, 4,000 characters, everywhere Locked (owner, voice, 11 Oct 2026)

A note is one entry under Notes: one block, or a short run of blocks (a heading and its list) added together, with one author and time (9.4).

  • One cap: 4,000 characters of text per note, the same for the app and for an assistant, and the same as one step (10.6). Markdown marks and a [photo:<id>] reference are not counted. There is no second, smaller limit anywhere: the app must not enforce a smaller cap (the earlier 600-character soft limit, the "Longer? Ask your assistant" prompt and the app/assistant split are void).
  • The note box is bounded; the page is not. A long note scrolls inside a bounded note box (in the editor and when shown) and never makes the page grow. The note is shown and edited in full in the app, whoever wrote it: no folding at a fixed length, no "change it through your assistant" for a long note, and the app never truncates. Over 4,000 the app and the server refuse alike (too_large).
  • Server-side guard, not a note cap: a version's own notes (what that version adds or rewords; inherited notes do not count) stay under 16 KB in total, so one version cannot grow the head cache without bound. Why that is safe: notes are stored per block and diffed per block (9.4), so the size of a note costs once, when it is written; a later typo fix in a long note stores one splice and one new block (~200 B); a version that inherits notes stores 0 bytes for them. Longer source material belongs in the recipe's provenance text (64 KB), stored once and not shown.

Was: 600 in the app's box, 4,000 from an assistant, edit in the app only up to 600. Replaced by the owner's single cap (voice, 11 October 2026).

10.7 Rich-text input

Markdown subset in, block document stored (9.4): paragraphs, #/##/### as heading levels, - and 1. lists with nesting up to 3, **bold**, *italics*, [label](https://url), > quote. Anything else (HTML, images by URL, tables) is rejected with invalid and a hint. When the assistant sends the whole new notes text, the server diffs it by block (matching unchanged blocks by content, then by position) so ids stay stable. get_version returns the notes as the same Markdown.

Not blocking: the assistant carries on and reports the photo as pending.
