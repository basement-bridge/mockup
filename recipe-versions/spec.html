Recipe versions: backend spec

What Recipe needs, as MCP tools, HTTP and storage, to support the versions and lifecycle mockup (V-D1 to V-D30). Written against Recipe's code as of 10 October 2026 (schema v5, 21 tools, server/src/mcp.ts, domain.ts, schema.ts).

Backend rules, to be filed as Recipe repo issues later. Nothing here is filed or built. Recipe's AGENTS.md says recipes and variations are immutable and that a schema change is an owner-reserved decision: this page proposes changing that rule, so it needs the owner's yes on an issue first. Everything stays in UAT until the owner tags a release. All Proposal.

1. Rules (replace "recipes and variations are immutable")
  1. BR1 Revisions are immutable. A revision's content, author, channel, words and time never change and are never deleted (DB triggers, as today's recipes_immutable).
  2. BR2 Versions and families are mutable pointers. Allowed to change: version name, state, head_revision_id; cover_photo_id (photos slice, P-D4); family name, usual_version_id, put_away. Nothing else. Every change appends a journal event with actor and channel.
  3. BR3 Nothing is deleted. Put away (state = put_away) replaces disabled. No DELETE on families, versions, revisions, cooks, suggestions.
  4. BR4 One usual per family, always. It must be a version in state trying or kept. Setting a trying version as usual also sets it kept. The usual cannot be put away.
  5. BR5 Parent is pinned. A version records parent_version_id and parent_revision_id. Later revisions of the parent never change the child. "Bring in the parent's fix" is a normal revise call by the caller.
  6. BR6 Optimistic concurrency. Every revise names base_revision_id; if it is not the head, the call fails with stale_base and returns the current head. Nothing is merged by the server.
  7. BR7 Author and channel on every write. actor_member_id comes from the session (platform token; legacy in standalone). channel is app for HTTP from Kitchie and assistant for MCP. The server sets both; the caller cannot.
  8. BR8 Assistant writes carry the person's words. On channel assistant, user_intent is required on create_version, revise_version, propose_change and set_version_state. On channel app it is optional (the tap is the intent). Same "never paraphrase into approval" wording as today's create_variation.
  9. BR9 Assistant scope (option 4 A). On channel assistant: may create versions (born trying, or suggested for a whole new recipe, see BR10), may revise a trying or suggested version, may NOT revise a kept version or the usual and may NOT set state kept, set the usual or put away: those return needs_person and the caller should use propose_change. (Option 4 B removes the revise restriction; option 4 C reads a per-member assistant_trusted flag.)
  10. BR10 Suggested is invisible to ordinary reads. A family whose only version is suggested is a draft (R-D12, gap G3): excluded from list, search, what_can_i_cook and ideas unless include_suggested. Accepting it (app, or a person through an assistant with words) moves it to trying.
  11. BR11 Temporary substitutions are still not persisted. Unchanged from today: "I used pork tonight" is a cook-log note, not a revision, unless the person says keep it.
  12. BR12 Missing stays missing. Unchanged: basis, value: null, no invented servings.
  13. BR13 Reasoning stays with the caller. The server never picks a version, never merges, never judges a substitution, never decides a try is good.

Option 5 on the overview asks how far to relax: A (this page) frozen revisions under mutable versions; B mutable rows with only the journal as history (simpler, but "see it as it was" and pinned parents need journal replay; not recommended); C keep today's immutability and add only state and usual (no edit in place: does not meet the brief).

2. Data model (schema v6)

Option 6 on the overview: A (recommended) each revision stores the whole resolved recipe, plus a computed changes list against its predecessor for display. B stores a sparse change set against the pinned parent revision (today's variation model, pinned). A is chosen because editing in place makes a chain of sparse change sets fragile (a fix in the middle of a chain must not move every child), and recipes are small (a few KB). Ingredient and step ids stay stable across revisions so diffs and cook ticks line up.

families      id, household_id, name, usual_version_id, put_away (0|1),
              created_at, created_by
              (mutable: name, usual_version_id, put_away)
versions      id, family_id, household_id, name, state, head_revision_id,
              parent_version_id NULL, parent_revision_id NULL,
              spun_to_family_id NULL, cover_photo_id NULL (P-D4),
              created_at, created_by, created_channel
              state IN ('suggested','trying','kept','put_away','spun_off')
              (mutable: name, state, head_revision_id, spun_to_family_id,
               cover_photo_id)
revisions     id, version_id, household_id, n (1,2,3 per version), kind,
              base_revision_id NULL, content_json (title, ingredients, steps,
              servings, times, metadata, source), changes_json (vs base),
              actor_member_id, channel, user_intent NULL, note NULL, created_at
              kind IN ('create','fix','adjust','restore','merge_parent','spin','migrated')
              IMMUTABLE, no delete
suggestions   id, version_id, household_id, base_revision_id, changes_json,
              title, user_intent, actor_member_id, channel, created_at,
              status ('open','applied','branched','dismissed'), resolved_by,
              resolved_at, result_revision_id NULL, result_version_id NULL
              (content immutable; status moves forward once, like nutrition_proposals)
cooks         id, household_id, family_id, version_id, revision_id, member_id,
              servings, verdict NULL ('keep','work','no'), line NULL,
              photo_ids_json NULL (0 to 3 photo ids, P-D13), cooked_at
              (append-only; gap G2)
member_prefs  member_id, version_id, starred, vote   (per member; V-D6)
member_settings member_id, assistant_trusted       (only for option 4 C)
legacy_ids    old_kind ('recipe'|'variation'), old_id, version_id, revision_id

Triggers: revisions and cooks no UPDATE, no DELETE; versions UPDATE only of the mutable columns, head_revision_id must point to a revision of the same version with a higher n (a restore is a new revision, so the head only moves forward); families.usual_version_id must be a version of the family in trying/kept; same-household checks as v5. search_text moves to versions and is rebuilt from the head revision when the head moves (derived, so mutable).

Nutrition: nutrition_observations.target_kind gains 'revision'. get_nutrition on a version reads the head revision's figures, and if there are none, returns the latest earlier revision's with for_revision and stale: true (V-D29). No recomputation.

4. Errors

Same shape as today, Error [code]: message. hint, with hints written for an assistant.

  • not_found, invalid, conflict, internal: unchanged.
  • stale_base: base_revision_id is not the head. Returns {head_revision_id, n, actor, created_at}. Hint: read the head with get_version, show the person both, retry on the new base only if they say so.
  • needs_person: an assistant tried to change a kept version or the usual, keep, set usual or put away. Hint: use propose_change with the person's words.
  • bad_transition: the state move is not allowed (e.g. suggested → kept). Lists the allowed moves.
  • is_usual: cannot put away or spin off the usual. Hint: set_usual on another version first.
  • no_change: the revise or create produced identical content. Nothing saved.
  • intent_required: assistant channel without user_intent (BR8).
  • not_allowed: household admin rule (V-D23) or app-only tool on the assistant channel.
  • too_many_open: suggestion cap per version.
  • invalid_change, parent_disabled: kept for the changes form; parent_disabled now means a put-away version as from (allowed from the app, refused for an assistant).

7. Migration of today's immutable data (v5 → v6)
  1. Back up first (infra runbook) and run on a copy in UAT; additive tables, old tables kept read-only for one release.
  2. Each recipes row → one family (same household, name = title) + version "Original" + revision 1 (kind migrated, content = the row, actor legacy, channel assistant if source.kind is conversation else app, user_intent null). State: kept if active, put_away if disabled. It is the usual.
  3. Each variations row (oldest first) → a version in its root's family, name = title or "Version n", revision 1 = resolve() of that variation at migration time (so content is exactly what callers saw), changes_json = its stored change set, user_intent and note copied, parent pinned to the parent's revision 1. State: kept if active, put_away if disabled.
  4. A disabled root with active variations: the family's usual becomes the most-used active variation (preferences.times_used, then newest); if none is active, the root stays the usual and the whole family is put away (a family-level put_away flag), so nothing that was hidden reappears. Owner to confirm.
  5. preferences → member_prefs for the household's first member (or legacy); times_used/last_used become synthetic cook rows marked migrated with no date detail beyond last_used.
  6. nutrition_observations on a recipe or variation → re-pointed via legacy_ids to the new revision 1 (observations are append-only: add a mapping, do not update rows).
  7. legacy_ids filled for every old id, so old ids in plans, chats and Kitchie keep resolving.
  8. Journal: one migration.v6 event per family with counts. Migration test from a real v5 file database with data at each shape (root only, chain of three, disabled root, disabled middle, nutrition attached).
  9. Rollback: v6 tables dropped, v5 tables untouched (they were not written during the release). After the owner removes the aliases, v5 tables can be archived.
